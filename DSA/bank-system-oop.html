Bank System OOP

Design a bank system with create_account, transfer, and get_top_activity. Incremental OOP/LLD exercise with production-readiness discussion.

Pattern: OOP / LLD Time: O(n) per transfer, O(n log n) top-k Space: O(n) Language: Java / Python

1. Problem Statement

Design a Bank class supporting account creation, money transfer between accounts, and retrieval of top-k accounts by transaction activity. This is a live OOP/LLD exercise where the interviewer builds requirements incrementally. The interviewer starts with a simple create_account and transfer, then adds get_top_activity, then asks about concurrency, persistence, and production hardening.

Required API:

  • 1. create_account(account_id, initial_balance) — returns true if created, false if already exists
  • 2. transfer(from_id, to_id, amount) — returns true if successful, false if insufficient funds or account missing
  • 3. get_top_activity(n) — returns the n account IDs with the most total transaction activity (sum of transfers in and out)

Sample operations:

bank = Bank()
bank.create_account("A", 1000)  -> true
bank.create_account("B", 500)   -> true
bank.create_account("A", 200)   -> false (already exists)
bank.transfer("A", "B", 200)    -> true  (A=800, B=700)
bank.transfer("A", "B", 9999)   -> false (insufficient funds)
bank.transfer("A", "C", 100)    -> false (C does not exist)
bank.transfer("B", "A", 100)    -> true  (B=600, A=900)
bank.get_top_activity(2)        -> ["A", "B"]  (A: 300 activity, B: 300 activity)

2. Pattern Recognition

▶

Why signals:

  • • Multiple operations on the same entity (account) → need OOP class encapsulation
  • • Fast lookup by account ID → HashMap
  • • Track running activity per account → counter field on Account
  • • Top-k query by activity → sort or heap
  • • Interviewer adds requirements over time → design for extensibility

Core pattern: OOP class design with a Bank facade, Account value object, HashMap for O(1) account lookup, activity counter per account, and a sort or min-heap for top-k retrieval.

3. Pattern Blueprint

▶

5-step OOP template for Bank System:

  1. 1 Define an Account class with fields: id, balance, activityCount
  2. 2 Define a Bank class with a HashMap<String, Account> for O(1) lookup
  3. 3 create_account: check if ID exists in map, if not create Account and put
  4. 4 transfer: validate both accounts exist, check sufficient funds, debit/credit atomically, increment activity on both
  5. 5 get_top_activity(n): collect accounts, sort by activityCount descending, return first n IDs

4. How to Think About It

▶

1 What are the entities?

Bank (the service/facade) and Account (the entity with balance and activity). Two classes. Keep Account as a simple value object initially.

2 How do I look up accounts fast?

HashMap<String, Account>. O(1) get and put. The key is the account_id string.

3 What does "activity" mean exactly?

Clarify with the interviewer. Default: total dollar amount moved (sum of all transfers in and out). Alternative: count of transactions. Ask which.

4 How do I get top-k efficiently?

Two options: (a) sort all accounts by activity descending, take first n — O(n log n). (b) min-heap of size n — O(n log k). For small k and large n, heap is better. For simplicity in an interview, sort is fine first, then optimize to heap if asked.

5 → What about concurrency?

Two concurrent transfers from the same account could both pass the balance check and overdraw. Production: use synchronized blocks, ReentrantLock per account, or optimistic concurrency with version numbers. State the issue and the fix.

5. Real-World Analogy

▶

Think of a bank branch with a ledger book. The Bank is the branch. Each Account is a page in the ledger book with the account holder's name, current balance, and a running tally of how much money has moved through that account.

When you transfer money, the teller flips to page A, checks the balance is enough, subtracts, then flips to page B and adds. The tally on both pages goes up by the transfer amount. The ledger book is the HashMap — the teller finds any page instantly by name.

For top activity, the manager asks "who are my most active customers?" The teller could flip through every page and sort (O(n log n)), or keep a smaller scoreboard of the top 10 and update it on each transfer (O(log k) with a heap). In production, the branch has multiple tellers, so the ledger needs a lock so two tellers do not write to the same page at the same time.

6. Build Your Intuition

▶

Q: Why use a HashMap instead of a List of Accounts?

List lookup by ID is O(n). HashMap is O(1). For a bank with millions of accounts, that is the difference between milliseconds and seconds per transfer.

Q: Should transfer be atomic?

Yes. Debit and credit must both succeed or both fail. If you debit A and then crash before crediting B, money is lost. In a single-threaded interview solution, the order does not matter. In production, use a database transaction or a saga with compensating actions.

Q: Sort vs heap for top-k?

Sort: O(n log n) time, O(n) space for the sorted list. Heap: O(n log k) time, O(k) space. For k much smaller than n (e.g., top 10 of 1M), heap is faster. For k close to n, sort is simpler and nearly as fast. In an interview, start with sort, offer heap as optimization.

Q: Why BigDecimal for balance?

Same as the payment validation problem. double has precision errors. BigDecimal is exact. For a bank system, this is non-negotiable.

7. How It Works (Step by Step)

▶
Step 1: Create Bank with empty HashMap<String, Account> accounts.
Step 2: create_account("A", 1000): "A" not in map, create Account(id="A", balance=1000, activity=0), put into map. Return true.
Step 3: create_account("B", 500): "B" not in map, create Account, put. Return true.
Step 4: create_account("A", 200): "A" already in map. Return false.
Step 5: transfer("A", "B", 200): get Account A (balance 1000 ≥ 200), get Account B. Debit A: 1000-200=800. Credit B: 500+200=700. A.activity += 200, B.activity += 200. Return true.
Step 6: transfer("A", "B", 9999): get A (balance 800 < 9999). Return false. No changes.
Step 7: transfer("A", "C", 100): get A ok, get C returns null. Return false. No changes.
Step 8: transfer("B", "A", 100): get B (balance 700 ≥ 100), get A. Debit B: 700-100=600. Credit A: 800+100=900. B.activity += 100 (now 300), A.activity += 100 (now 300). Return true.
Step 9: get_top_activity(2): collect [A(activity=300), B(activity=300)]. Sort descending by activity. Return ["A", "B"] (or ["B", "A"] if tie broken by insertion order).

10. Complexity Deep Dive
▶
  

      

        
Time Complexity

        
create_account: O(1) — HashMap put.

        
transfer: O(1) — two HashMap gets, balance checks, arithmetic.

        
get_top_activity(n): O(n log n) with sort, O(n log k) with min-heap of size k.

        
For m total operations, amortized O(m) for create+transfer, plus O(n log n) per top-k call.

      

      

        
Space Complexity

        
O(n) where n is the number of accounts. The HashMap stores n Account objects. Each Account stores id, balance, activity — O(1) per account.

        
get_top_activity with sort uses O(n) for the sorted list. With heap, O(k) for the heap.

      

    

  







  
11. From Brute Force to Optimal
▶
  

      

        
Naive: List of Accounts, Linear Search

        
class Bank {
  List accounts;
  transfer(from, to, amt) {
    Account a = find(from); // O(n)
    Account b = find(to);   // O(n)
    ...
  }
}

        
transfer is O(n) due to linear search. For 1M accounts and 10M transfers, that is 10 trillion operations. Unusable.

      

      

        
Optimal: HashMap + Sort/Heap

        
class Bank {
  Map accounts;
  transfer(from, to, amt) {
    Account a = accounts.get(from); // O(1)
    Account b = accounts.get(to);   // O(1)
    ...
  }
}

        
transfer is O(1). For 10M transfers, 10M operations. 1 million times faster at scale.

      

    

  







  
12. Edge Cases & Gotchas
▶
  

      

        
Transfer to self

        
from_id == to_id. Should this be allowed? Clarify. Default: reject (no-op, return false) or allow (balance unchanged, activity increases). State your assumption.

      

      

        
Negative or zero transfer amount

        
Reject. amount must be > 0. A negative transfer would be a reverse transfer, which is a different operation. Zero is a no-op.

      

      

        
Initial negative balance

        
Should create_account allow negative initial balance? Typically no. Reject if initial_balance < 0. Clarify with interviewer.

      

      

        
Tie in top-k activity

        
Two accounts with the same activity. Which comes first? Define a tiebreaker: account ID alphabetical, or insertion order. State it explicitly.

      

      

        
n larger than number of accounts

        
get_top_activity(100) but only 5 accounts exist. Return all 5 sorted, or return error? Default: return all available, do not error.

      

    

  







  
13. Flashcards
▶
  

      

        Q1: What is the time complexity of transfer?
        
O(1). Two HashMap gets, balance comparison, two arithmetic operations, two activity increments. All O(1).

      

      

        Q2: How do you optimize get_top_activity if called frequently?
        
Maintain a sorted structure (TreeMap by activity or a balanced BST) updated on each transfer. get_top_activity becomes O(k) to extract top k. Trade-off: transfer becomes O(log n) instead of O(1) due to tree update. Alternatively, use a min-heap of size k and lazy-update on query.

      

      

        Q3: How do you handle concurrent transfers from the same account?
        
Two threads both read balance 1000, both check 1000 ≥ 600, both debit 600, balance becomes -200. Fix: synchronized block on the account, or ReentrantLock per account, or optimistic concurrency with version number (CAS).

      

      

        Q4: Why BigDecimal instead of double for balance?
        
double has floating-point precision errors. 0.1 + 0.2 != 0.3. BigDecimal is exact. For a bank system, precision errors accumulate over millions of transactions and cause reconciliation failures.

      

      

        Q5: How would you persist this to a database?
        
Accounts table with id, balance, activity. Transfer is a DB transaction: SELECT both accounts FOR UPDATE, check balance, UPDATE both, INSERT into transactions table, COMMIT. The FOR UPDATE lock prevents concurrent overdraw.

15. Common Mistakes
▶
  

      
    
        
  • •  Using double for balance. Precision errors. Use BigDecimal.
    • 
        
  • •  Not checking account existence before balance check. NullPointerException. Always null-check first.
    • 
        
  • •  Debiting before checking sufficient funds. Check balance ≥ amount first, then debit. Otherwise you overdraw.
    • 
        
  • •  Not handling self-transfer. from == to. Clarify behavior. Default: reject or no-op.
    • 
        
  • •  Forgetting to increment activity on both accounts. Activity is total money moved, so both sender and receiver get credited.
    • 
        
  • •  Not defining tiebreaker for top-k. Two accounts with same activity, which comes first? State the rule.
    • 
        
  • •  Not discussing concurrency. Senior interview expects you to raise the race condition and propose a fix.

19. Where This Pattern Meets System Design
▶
  

      

        
In-memory HashMap → Distributed Account Service

        
The coding exercise uses an in-memory HashMap. Production uses a sharded database (PostgreSQL with Citus, or Cassandra) with accounts partitioned by account_id hash. Each partition handles a range of accounts.

      

      

        
O(1) transfer → Two-Phase Commit or Saga

        
If both accounts are on the same shard, a local DB transaction suffices. If on different shards, use a saga with compensating actions or two-phase commit. For Capital One GPN scale, saga with idempotency is preferred over 2PC for availability.

      

      

        
Activity counter → Event-Sourced Activity Stream

        
Instead of a mutable activity field, every transfer publishes an event to Kafka. Activity is computed by aggregating events. Enables replay, audit, and real-time analytics without mutating the account record.

      

      

        
get_top_activity → Pre-aggregated Leaderboard

        
For frequent top-k queries, maintain a Redis Sorted Set updated on each transfer. ZREVRANGE returns top-k in O(log n). Or use a streaming aggregation (Flink/Spark) that periodically writes top-k to a cache.

      

      

        
Single Bank class → Microservices + API Gateway

        
Account Service (CRUD), Transfer Service (orchestration), Activity Service (analytics), Audit Service (immutable log). API Gateway routes requests. Each service has its own database (polyglot persistence).

Java

        
import java.math.BigDecimal;
import java.util.*;
import java.util.stream.Collectors;

class Account {
    final String id;
    BigDecimal balance;
    BigDecimal activity;
    Account(String id, BigDecimal balance) {
        this.id = id;
        this.balance = balance;
        this.activity = BigDecimal.ZERO;
    }
}

class Bank {
    private final Map<String, Account> accounts = new HashMap<>();

    public boolean createAccount(String accountId, BigDecimal initialBalance) {
        if (accounts.containsKey(accountId)) return false;
        if (initialBalance.compareTo(BigDecimal.ZERO) < 0) return false;
        accounts.put(accountId, new Account(accountId, initialBalance));
        return true;
    }

    public boolean transfer(String fromId, String toId, BigDecimal amount) {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) return false;
        if (fromId.equals(toId)) return false;
        Account from = accounts.get(fromId);
        Account to = accounts.get(toId);
        if (from == null || to == null) return false;
        if (from.balance.compareTo(amount) < 0) return false;
        from.balance = from.balance.subtract(amount);
        to.balance = to.balance.add(amount);
        from.activity = from.activity.add(amount);
        to.activity = to.activity.add(amount);
        return true;
    }

    public List<String> getTopActivity(int n) {
        return accounts.values().stream()
            .sorted((a, b) -> b.activity.compareTo(a.activity))
            .limit(n)
            .map(a -> a.id)
            .collect(Collectors.toList());
    }
}

      

      

        
Python

        
from decimal import Decimal
from typing import List

class Account:
    def __init__(self, account_id: str, balance: Decimal):
        self.id = account_id
        self.balance = balance
        self.activity = Decimal("0")

class Bank:
    def __init__(self):
        self.accounts: dict[str, Account] = {}

    def create_account(self, account_id: str, initial_balance: Decimal) -> bool:
        if account_id in self.accounts:
            return False
        if initial_balance < Decimal("0"):
            return False
        self.accounts[account_id] = Account(account_id, initial_balance)
        return True

    def transfer(self, from_id: str, to_id: str, amount: Decimal) -> bool:
        if amount <= Decimal("0"):
            return False
        if from_id == to_id:
            return False
        from_acct = self.accounts.get(from_id)
        to_acct = self.accounts.get(to_id)
        if not from_acct or not to_acct:
            return False
        if from_acct.balance < amount:
            return False
        from_acct.balance -= amount
        to_acct.balance += amount
        from_acct.activity += amount
        to_acct.activity += amount
        return True

    def get_top_activity(self, n: int) -> List[str]:
        sorted_accounts = sorted(self.accounts.values(), key=lambda a: a.activity, reverse=True)
        return [a.id for a in sorted_accounts[:n]]

      

    

  







  
21. Follow-Up Questions
▶
  

      

        Q: How would you handle a transfer between accounts on different shards?
        
Saga pattern. Step 1: debit from-account (local transaction on shard A). Step 2: credit to-account (local transaction on shard B). If step 2 fails, compensating action: refund from-account. Use idempotency keys so retries do not double-credit.

      

      

        Q: How would you make get_top_activity O(1)?
        
Maintain a Redis Sorted Set (ZSET) with account_id as member and activity as score. On each transfer, ZINCRBY both accounts. get_top_activity is ZREVRANGE which is O(log n). For true O(1), cache the top-k in a separate key updated by a streaming job.

      

      

        Q: What if the bank needs to handle 100K transfers per second?
        
In-memory HashMap will not work. Shard the account store by account_id hash across N database nodes. Each transfer goes to the shard(s) owning the accounts. Use connection pooling, async I/O, and batch writes. Kafka for event streaming. Cache hot accounts in Redis.

      

      

        Q: How do you audit every transfer?
        
Every transfer writes an immutable record to a transactions table: transaction_id, from_id, to_id, amount, timestamp, status. Publish to Kafka for downstream consumers. The audit table is append-only, never updated or deleted. Retention is regulatory (7 years for banking).

      

      

        Q: How do you handle a crash mid-transfer?
        
Use a write-ahead log (WAL) or database transaction. The transfer is committed atomically. If the process crashes after debit but before credit, the transaction rolls back on recovery. If using a saga, the compensating action (refund) is triggered by a timeout or failure event.

Core code shape:

      
class Bank {
  Map accounts = new HashMap<>();

  boolean createAccount(id, balance) {
    if (accounts.containsKey(id)) return false;
    accounts.put(id, new Account(id, balance));
    return true;
  }

  boolean transfer(from, to, amount) {
    if (amount <= 0 || from.equals(to)) return false;
    Account a = accounts.get(from), b = accounts.get(to);
    if (a == null || b == null) return false;
    if (a.balance < amount) return false;
    a.balance -= amount; b.balance += amount;
    a.activity += amount; b.activity += amount;
    return true;
  }

  List getTopActivity(n) {
    return accounts.values().stream()
      .sorted(by activity desc)
      .limit(n).map(id).collect();
  }
}
