Merge Intervals

Time: O(n log n) Space: O(n) Sorting + Sweep

1. Problem Statement

Given an array of intervals where intervals[i] = [start_i, end_i], merge all overlapping intervals, and return an array of the non-overlapping intervals that cover all the intervals in the input.

Constraints:

  • 1 ≤ intervals.length ≤ 10^4
  • intervals[i].length == 2
  • 0 ≤ start_i ≤ end_i ≤ 10^4

Example: Input: [[1,3],[2,6],[8,10],[15,18]] → Output: [[1,6],[8,10],[15,18]]

▶

Signal words: "merge", "overlapping", "intervals", "non-overlapping", "cover all".

3. Pattern Blueprint

▶ 
merged_intervals = []
sort intervals by start_time
add first interval to merged_intervals
for each next interval in intervals:
    last_merged = merged_intervals[-1]
    if interval.start <= last_merged.end:   # overlap
        last_merged.end = max(last_merged.end, interval.end)
    else:                                    # no overlap
        merged_intervals.append(interval)
return merged_intervals

The skeleton is the same for every interval problem. What changes is the overlap condition and what you do on overlap (merge, count, skip, split).

4. How to Think About It

▶

The core insight is that overlapping intervals are only detectable when they're sorted by start time. If intervals are scattered, two intervals that overlap might be far apart in the array and you'd never know to compare them without checking every pair (O(n²)).

Once sorted by start time, any interval that overlaps with the current one must be the next interval in the sorted order (or the one after that, etc.). Overlaps become contiguous runs in the sorted array.

This converts the problem from "compare every pair" to "walk left to right and merge adjacent overlaps" — O(n log n) for the sort, O(n) for the sweep.

The second insight: when two intervals overlap, the merged interval's end is the max of the two ends, not the end of the later one. [[1,4],[2,3]] merges to [[1,4]], not [[1,3]].

5. Real-World Analogy

▶

Imagine you're a wedding planner with a stack of vendor availability slips, each showing a date range the vendor is free. The slips are in random order.

To build a single "when is everyone free" calendar, you first sort the slips by start date. Then you walk through the sorted stack: if the next slip starts before or on the day the current one ends, they overlap and you combine them into one bigger window (ending on whichever ends later). If it starts after, it's a new separate window.

You'd never try to merge slips without sorting first — you'd miss overlaps between slips that happen to be far apart in the stack.

8. How It Works (Step by Step)

▶

Step 1: Sort intervals by start time. This is the O(n log n) cost. After sorting, overlaps are contiguous.

Step 2: Initialize merged_intervals with the first interval. This avoids an empty-list edge case when checking merged_intervals[-1].

Step 3: For each remaining interval, compare its start with the end of the last interval in merged_intervals.

Step 4: If start ≤ last_end → overlap. Update last_end = max(last_end, current_end). Do NOT append — we're extending the last merged interval.

Step 5: If start > last_end → no overlap. Append [start, end] as a new entry in merged_intervals.

Step 6: Return merged_intervals.

10. Complexity Deep Dive

▶

Time: O(n log n) — dominated by the sort. The sweep is O(n) because each interval is visited exactly once. The sort is O(n log n) comparisons. So overall O(n log n) + O(n) = O(n log n).

Space: O(n) — for the merged_intervals output list. In the worst case (no overlaps), the output is the same size as the input. Some languages sort in-place (O(1) extra for the sort), but the output list is still O(n).

Could we do better? If intervals are already sorted by start, the sweep alone is O(n). But the general case requires the sort. There's no known O(n) general solution because detecting overlaps in unsorted input is at least as hard as sorting (comparison model lower bound Ω(n log n)).

11. From Brute Force to Optimal — Every Decision & Why

▶

Each version below is forced by an edge case the previous version gets wrong. Read this as a chain of decisions, not a jump.

v0

Naive: compare every pair

merged_intervals = []
for i in range(len(intervals)):
    for j in range(i + 1, len(intervals)):
        if intervals[i][1] >= intervals[j][0] and intervals[j][1] >= intervals[i][0]:
            # overlap — but which pair do we merge? and what about chains?
            pass
return merged_intervals

Works on: nothing useful. Even if you detect an overlap, you can't just merge two intervals — overlaps chain ([1,3],[2,6],[5,8] all overlap transitively).

Breaks on: any input with chained overlaps. And it's O(n²) even when it works. The problem is that without sorting, overlaps aren't contiguous, so you'd need to re-scan after every merge.

v1

+ Sort by start (fixes contiguity)

intervals.sort(key=lambda interval: interval[0])
merged_intervals = [intervals[0]]
for start, end in intervals[1:]:
    last_end = merged_intervals[-1][1]
    if start <= last_end:
        merged_intervals[-1][1] = end
    else:
        merged_intervals.append([start, end])
return merged_intervals

Decision: Sort by start time first. Now overlaps are contiguous runs. Walk left to right, merge or append. O(n log n). ✓

Breaks on: [[1,4],[2,3]] → 2 ≤ 4 so overlap → set end = 3 → [[1,3]]. WRONG. The merged interval should be [[1,4]] — the second interval is fully inside the first, and we shrank the result.

v2

+ max() on merge (fixes contained intervals) — FINAL

intervals.sort(key=lambda interval: interval[0])
merged_intervals = [intervals[0]]
for start, end in intervals[1:]:
    last_end = merged_intervals[-1][1]
    if start <= last_end:
        merged_intervals[-1][1] = max(last_end, end)
    else:
        merged_intervals.append([start, end])
return merged_intervals

Decision: On overlap, set last_end = max(last_end, end), not just end. Now [[1,4],[2,3]] → max(4,3) = 4 → [[1,4]]. ✓

Handles everything: chained overlaps, contained intervals, touching intervals ([1,4],[4,5] → [1,5]), single interval, all-disjoint, all-overlapping. Time O(n log n), space O(n).

12. Common Mistakes

▶

● Forgetting max() on merge — the most common bug. Sets end to the current interval's end instead of the larger of the two.

● Sorting by end time instead of start time. Works sometimes but breaks on [[1,4],[0,2]] — sorted by end gives [[0,2],[1,4]] which happens to work, but [[1,4],[0,0]] sorted by end gives [[0,0],[1,4]] and misses that [0,0] doesn't overlap [1,4]... actually that's fine. The real break is [[2,3],[1,5]] — sorted by end gives [[2,3],[1,5]], sweep sees 3 < 1? No. The point is: sort by start, always.

● Using < instead of ≤ for the overlap check. [1,4],[4,5] should merge to [1,5] (touching intervals overlap), but 4 < 4 is false so they'd stay separate.

● Appending on overlap instead of extending. Creates duplicate entries in the result.

● Not seeding merged_intervals with the first interval, then checking merged_intervals[-1] on an empty list → IndexError.

13. Edge Cases & Gotchas

▶

Single interval: [[1,2]] → loop never enters, return [[1,2]]. Handled by seeding.

All disjoint: [[1,2],[3,4],[5,6]] → no merges, output = input.

All overlapping into one: [[1,4],[2,3],[3,5]] → [[1,5]]. Tests the max() on chained merges.

Contained interval: [[1,4],[2,3]] → [[1,4]]. The bug that forces max().

Touching intervals: [[1,4],[4,5]] → [[1,5]]. Use ≤ not <.

Unsorted input: [[2,6],[1,3],[8,10],[15,18]] → must sort first → [[1,6],[8,10],[15,18]].

Duplicate intervals: [[1,4],[1,4]] → [[1,4]]. Overlap check 1 ≤ 4 handles it.

Q: Why sort by start, not end? | A: Sorting by start makes overlaps contiguous in the array, so a single left-to-right sweep catches every merge.

class Solution:
    def merge(self, intervals: List[List[int]]) -> List[List[int]]:
        intervals.sort(key=lambda interval: interval[0])
        merged_intervals = [intervals[0]]
        for start, end in intervals[1:]:
            last_end = merged_intervals[-1][1]
            if start <= last_end:
                merged_intervals[-1][1] = max(last_end, end)
            else:
                merged_intervals.append([start, end])
        return merged_intervals

Java

import java.util.*;

class Solution {
    public int[][] merge(int[][] intervals) {
        Arrays.sort(intervals, (a, b) -> a[0] - b[0]);
        List merged_intervals = new ArrayList<>();
        merged_intervals.add(intervals[0]);
        for (int[] interval : intervals) {
            int[] last_merged = merged_intervals.get(merged_intervals.size() - 1);
            if (interval[0] <= last_merged[1]) {
                last_merged[1] = Math.max(last_merged[1], interval[1]);
            } else {
                merged_intervals.add(interval);
            }
        }
        return merged_intervals.toArray(new int[merged_intervals.size()][]);
    }
}

21. Follow-Up Questions

▶
Q1: What if the input is already sorted by start? | A: The sweep alone is O(n). You can skip the sort. In practice, check if sorted first if you expect sorted input.
Q2: What if intervals are sorted by end time instead? | A: Re-sort by start, or process right-to-left merging on the start side. Sorting by start is the standard sweep-line approach.
Q3: How would you handle streaming intervals (can't sort all upfront)? | A: Insert each new interval into a sorted structure (balanced BST), then merge on query. Or use an interval tree for overlap queries.
Q4: What if you need to return the original indices of merged groups? | A: Decorate each interval with its index before sorting, carry the index through the merge, and track which original indices each merged interval absorbed.
Q5: How would you merge intervals from multiple machines in a distributed setting? | A: Each machine sorts and merges locally, then a reducer merges the sorted merged lists (merge-sort style, since each machine's output is already sorted by start).
