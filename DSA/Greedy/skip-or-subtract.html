Skip or Subtract

One-pass simulation · Greedy · Time O(n) · Space O(1)

1. Problem Statement

You are given two positive integers x and y, and a sequence of positive integers numbers. Iterate through numbers from left to right. For each numbers[i]:

  • •If numbers[i] is greater than both x and y, skip it (do nothing).
  • •Otherwise, subtract numbers[i] from the larger of x and y.
  • •If x == y (tie), subtract from x.

Return the count of integers in numbers that were skipped.

Example:

x = 8, y = 12, numbers = [5, 6, 6, 3, 1, 1, 2] → returns 2

Skipped values: 3 (greater than both x=5 and y=6 at that point) and 2 (greater than both x=3 and y=6).

2. Pattern Recognition

▶

Signal words: "iterate left to right", "subtract from the larger", "skip if greater than both", "return the count". This is a simulation problem — the order is fixed, the operation at each step is fully determined by the current state, and there is no choice to optimize.

When to reach for this pattern: Whenever the problem statement describes a deterministic, left-to-right process with no branching decisions. The word "skip" combined with a fixed iteration order signals simulation, not DP or greedy-choice.

Key insight: There is no decision to make at each step. The problem tells you exactly what to do: skip if too large, otherwise subtract from the larger (tie → x). This is a one-pass simulation, not an optimization problem. The "trick" is recognizing that no trick is needed.

  • Fixed left-to-right order → no sorting, no reordering
  • Deterministic operation at each step → simulation, not DP
  • Only tracking x, y, skip_count → O(1) space

Approaches considered before settling on simulation: Always brainstorm variants before committing. The fixed-order constraint rules out most optimization approaches, but naming them forces you to understand why simulation wins.

3. Pattern Blueprint

▶
  • 1Initialize skip_count = 0
  • 2For each value in numbers:
  • 3If value > x AND value > y: increment skip_count, continue
  • 4Else if x >= y: x -= value
  • 5Else: y -= value
  • 6Return skip_count

4. How to Think About It

▶

The first instinct when seeing "subtract from the larger" is to think there's a strategic choice: which side should I subtract from to minimize future skips? This is a trap. The problem removes the choice — it tells you exactly what to do at each step.

The only "decision" is the skip check: if the current value is greater than both x and y, you can't subtract it from either without going negative (the problem implies positive integers only, and subtracting a larger value would make x or y negative, which isn't allowed). So you skip.

The tie rule (x == y → subtract from x) is arbitrary but deterministic. It exists because "the larger" is ambiguous when they're equal, so the problem picks one. Your job is to implement the rule, not question it.

Because there's no choice, there's no DP, no greedy optimization, no backtracking. You just simulate. The optimal solution is the brute-force solution — they're the same thing. This is the key insight: recognizing when a problem is not an optimization problem.

5. Real-World Analogy

▶

Two buckets, one stream of water: You have two buckets, x and y, each holding some water. A conveyor belt brings cups of water one at a time, left to right.

For each cup: if the cup is bigger than both buckets combined can hold, set it aside (skip). Otherwise, pour it into the emptier bucket (the one with more current capacity — i.e., the "larger" remaining value). If both buckets have the same remaining capacity, pour into bucket x by convention.

Mapping:

  • x, y = bucket capacities (remaining space)
  • numbers = cups on the conveyor belt
  • skip = cup too big for either bucket, set it aside
  • subtract from larger = pour into the bucket with more room
  • tie → x = when both have equal room, use bucket x by convention

You don't get to reorder the cups or choose which bucket to fill — the rule is fixed. You just count how many cups were too big.

8. How It Works (Step by Step)

▶
1Initialize skip_count = 0. Keep x and y as mutable variables.
2For each value in numbers (left to right, no reordering):
3Skip check: If value > x AND value > y, the value is too large for either variable. Increment skip_count and move to the next value.
4Subtract: Otherwise, subtract from the larger. If x >= y (includes the tie case), do x -= value. Else y -= value.
5Return skip_count after the loop ends.

The >= in step 4 is what handles the tie: when x == y, x >= y is true, so we subtract from x. No separate tie branch needed.

10. From Brute Force to Optimal — Every Decision & Why

▶

v0 — Brute Force: simulation with explicit branches

Time: O(n) Space: O(1) 
def solution_bruteforce(x, y, numbers):
    skip_count = 0
    for value in numbers:
        if value > x and value > y:
            skip_count += 1
        elif x >= y:
            x -= value
        else:
            y -= value
    return skip_count

Why this is "brute force": It's the most direct translation of the problem statement into code. Three branches: skip, subtract from x, subtract from y. It works on the happy path and is already O(n) / O(1). But the branch structure is slightly redundant — the elif x >= y duplicates the tie logic.

v_final — Clean simulation with continue

Time: O(n) Space: O(1) 
def solution(x, y, numbers):
    skip_count = 0
    for value in numbers:
        if value > x and value > y:
            skip_count += 1
            continue
        if x >= y:
            x -= value
        else:
            y -= value
    return skip_count

Why final: Same O(n) / O(1) complexity, but the continue separates the skip logic from the subtract logic, making each branch's responsibility clearer. The x >= y check naturally handles the tie case without a separate branch. This is the version used in Section 20.

Principle: Every line of complexity was earned by a specific input the previous version failed on. If you can't name the edge case that forced a line, you don't understand why it's there. In this problem, there's no complexity to earn — the optimal solution IS the simulation. Recognizing when a problem is not an optimization problem is itself a skill.

11. Complexity Deep Dive

▶

Time: O(n) — Single pass through numbers. Each element is visited exactly once. No nested loops, no sorting, no backtracking.

Space: O(1) — Only three variables are tracked: x, y, and skip_count. The input array is not copied or modified.

Why this is optimal: You must examine every element at least once to decide whether to skip or subtract — that's a lower bound of Ω(n). The simulation achieves this bound exactly. No algorithm can do better.

12. Edge Cases & Gotchas

▶
  • Empty numbers: numbers = [] → returns 0. The loop doesn't execute.
  • All skipped: Every value > both x and y → returns len(numbers). x and y unchanged.
  • None skipped: Every value ≤ at least one of x, y → returns 0.
  • Tie case (x == y): Must subtract from x, not y. The x >= y check handles this — do NOT use x > y or the tie goes to y.
  • Skip condition is strict >: Use value > x and value > y, NOT >=. If value == x and value > y, you can still subtract from x (x becomes 0), so it's not a skip.
  • x or y reaches 0: After subtraction, x or y can become 0. Subsequent values > 0 will be > that variable, pushing more skips toward the other side. This is expected behavior.

13. Common Mistakes

▶
  • Using >= in the skip check: if value >= x and value >= y is WRONG. It skips when value == x, but you can still subtract from x (resulting in 0). Skip only when value > x AND value > y.
  • Tie goes to the wrong variable: Using if x > y: x -= value else: y -= value sends the tie to y. The problem says tie → x. Use x >= y.
  • Reordering numbers: Sorting numbers to "optimize" changes the answer. The problem requires left-to-right processing.
  • Over-engineering with DP: Building a memoization table on (x, y, index) when there's no choice to make. This wastes time and space for no benefit.

14. Flashcards

▶
Q: What is the skip condition?

Skip when value > x AND value > y (strict >, not >=). The value must be too large for both variables.

Q: What happens on a tie (x == y)?

Subtract from x. Implement this with if x >= y: x -= value — the >= naturally includes the tie case.

Q: What is the time and space complexity?

Time O(n), Space O(1). Single pass, three variables. This is optimal — you must examine every element.

Q: Why is there no DP or greedy optimization?

Because there's no choice to make at each step. The operation is fully determined by the current state (skip if too large, else subtract from larger). DP and greedy are for when you have choices to optimize.

Q: Can you reorder numbers to minimize skips?

No. The problem requires processing "left to right". Reordering changes the answer and violates the constraint.

15. Where It Is Used (Real World)

▶

Resource allocation under streaming constraints: Two servers (x, y) with fixed capacity. Incoming requests (numbers) must be routed to the server with more remaining capacity. Requests exceeding both capacities are dropped (skipped). This models load balancing with a simple "emptier server wins" policy.

Budget depletion tracking: Two budgets (x, y) consumed by a stream of expenses. Each expense is charged to the larger remaining budget. Expenses exceeding both budgets are rejected. The skip count is the number of rejected expenses.

Game state simulation: Two health pools (x, y) reduced by a sequence of attacks. Each attack hits the healthier pool. Attacks that would exceed both pools are dodged. The skip count is the number of dodged attacks.

19. Where This Pattern Meets System Design

▶

In a streaming system, this pattern maps to stateful stream processing: a worker maintains a small fixed state (x, y) and processes an unbounded stream of events (numbers), making a deterministic decision per event.

Scale considerations:

  • If the stream is unbounded, you can't store it — the O(1) space property is essential.
  • If events arrive at high throughput, the per-event decision must be O(1) — no sorting, no lookup.
  • If the state (x, y) is large or distributed, you'd shard by key and aggregate the skip counts.
  • Fault tolerance: checkpoint (x, y, skip_count) periodically so the worker can resume after a crash.

21. Follow-Up Questions

▶
  • What if x and y can go negative? The problem says positive integers, but if they could go negative, the skip condition would need to change — you'd skip only if subtracting would make both negative, or you'd allow negative values and never skip.
  • What if you could choose which variable to subtract from? Then it becomes a DP/greedy problem: minimize skips by choosing the optimal target at each step. The state is (x, y, index), and you'd memoize.
  • What if numbers is a stream (unbounded)? The O(1) space solution handles this naturally — you never store the stream, just process element by element.
  • What if there are k variables instead of 2? Generalize: skip if value > max(all variables), else subtract from the largest. Time stays O(n), space O(k).
