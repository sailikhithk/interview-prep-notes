Merged Byte Ranges (Chunked Upload)

Interval merging · Line Sweep · Time O(n²) optimal / O(n² log n) brute · Space O(n)

1. Problem Statement

A user is uploading a big file to your server in chunks. Each chunk is an inclusive byte interval [l, r] (1-based). After each received chunk, return the current set of merged consecutive byte ranges received so far. Chunks may overlap or fully duplicate previous chunks.

Given a list of chunks where chunks[i] = [l, r], return a list where the i-th element is the merged list of consecutive ranges after processing chunks 0 through i.

Example:

chunks = [[1,3], [5,7], [2,5], [8,10]]

After [1,3]: [[1,3]]. After [5,7]: [[1,3],[5,7]]. After [2,5]: merges [1,3]+[2,5]+[5,7] = [[1,7]]. After [8,10]: [[1,7],[8,10]] (adjacent, merges to [[1,10]]).

2. Pattern Recognition

▶

Signal words: "inclusive interval [l, r]", "merged consecutive byte ranges", "overlap or fully duplicate", "after each received chunk". This is a streaming interval merge problem — you maintain a normalized set of non-overlapping, non-adjacent intervals and update it incrementally.

When to reach for this pattern: Whenever a problem asks you to maintain merged intervals under insertions. The key invariant is: keep the interval list sorted, non-overlapping, and non-adjacent at all times. Each new chunk merges into this list.

Key insight: "Consecutive" means adjacent intervals merge too — [1,3] and [4,6] merge into [1,6] because they're consecutive (no gap). The merge condition is start ≤ prev_end + 1, not start ≤ prev_end. The +1 is what captures "consecutive".

  • "Merged consecutive ranges" → adjacent intervals (gap of 1) merge
  • "After each chunk" → streaming, output after every insertion
  • Maintain sorted non-overlapping invariant → incremental merge

3. Pattern Blueprint

▶
  • 1Maintain intervals = sorted, non-overlapping, non-adjacent list. Initially empty.
  • 2For each new chunk [left, right]:
  • 3Copy before: Append all intervals with end + 1 < left (strictly before, no touch).
  • 4Merge: Expand [merged_left, merged_right] over all intervals with start ≤ merged_right + 1 (overlap or touch).
  • 5Copy after: Append the merged interval, then all remaining intervals.
  • 6Append a copy of intervals to result (snapshot after this chunk).

4. How to Think About It

▶

The key insight is the invariant: intervals is always kept sorted, non-overlapping, and non-adjacent. If you maintain this, each new chunk only affects a contiguous slice of the list — the intervals that overlap or touch it.

The merge condition start ≤ merged_right + 1 is what captures "consecutive". If the new chunk ends at 5 and an existing interval starts at 6, they're consecutive (no gap), so they merge into [..., 6]. Without the +1, you'd leave [1,5] and [6,10] separate when they should be [1,10].

The three-phase scan (copy before, merge, copy after) is a single pass through the sorted list. You don't re-sort — the list is already sorted, and the new chunk merges into its correct position.

The snapshot copy at the end is critical: result.append([iv[:] for iv in intervals]). If you append intervals directly, later mutations corrupt earlier snapshots. The iv[:] copies each interval so future merges don't affect past results.

5. Real-World Analogy

▶

Booking seats in a theater: A theater has seats 1 to N. People book ranges of consecutive seats. After each booking, you want to show the current "occupied blocks" — adjacent bookings merge into one block.

If person A books seats 1-3 and person B books seats 4-6, the occupied block is 1-6 (consecutive, no gap). If person C then books seat 8, the blocks are [1-6, 8-8] — seat 7 is still free, so they don't merge.

Mapping:

  • [l, r] = a booking of seats l through r
  • merged ranges = current occupied blocks (adjacent bookings merge)
  • overlap = two bookings sharing seats
  • consecutive (touch) = bookings with no gap between them (seat 3 and seat 4)

8. How It Works (Step by Step)

▶
1Initialize intervals = [] (sorted, non-overlapping, non-adjacent) and result = [].
2For each chunk [left, right]: build new_intervals by scanning intervals in three phases.
3Phase 1 (copy before): While intervals[i].end + 1 < left, the interval is strictly before the new chunk (no touch). Copy it as-is.
4Phase 2 (merge): While intervals[i].start ≤ merged_right + 1, the interval overlaps or touches the growing merged range. Expand merged_left = min(...), merged_right = max(...).
5Phase 3 (copy after): Append the merged [merged_left, merged_right], then copy all remaining intervals.
6Snapshot: Append [iv[:] for iv in intervals] to result — a deep copy of the current state.

10. From Brute Force to Optimal — Every Decision & Why

▶

v0 — Brute Force: re-sort + merge from scratch each time

Time: O(n² log n) Space: O(n) 
def solution_bruteforce(chunks):
    seen = []
    answer = []
    for left, right in chunks:
        seen.append([left, right])
        seen.sort()
        merged = []
        for cur_left, cur_right in seen:
            if not merged or cur_left > merged[-1][1] + 1:
                merged.append([cur_left, cur_right])
            else:
                merged[-1][1] = max(merged[-1][1], cur_right)
        answer.append([iv[:] for iv in merged])
    return answer

Flaw: After each chunk, it re-sorts ALL chunks seen so far and re-merges from scratch. The sort is O(k log k) per chunk, giving O(n² log n) total. Works correctly but wastes time re-merging intervals that were already merged.

v_final — Incremental merge into sorted list

Time: O(n²) Space: O(n) 
def solution(chunks):
    intervals = []
    result = []
    for left, right in chunks:
        new_intervals = []
        i = 0
        n = len(intervals)
        while i < n and intervals[i][1] + 1 < left:
            new_intervals.append(intervals[i])
            i += 1
        merged_left, merged_right = left, right
        while i < n and intervals[i][0] <= merged_right + 1:
            merged_left = min(merged_left, intervals[i][0])
            merged_right = max(merged_right, intervals[i][1])
            i += 1
        new_intervals.append([merged_left, merged_right])
        while i < n:
            new_intervals.append(intervals[i])
            i += 1
        intervals = new_intervals
        result.append([iv[:] for iv in intervals])
    return result

Why final: Maintains the sorted non-overlapping invariant. Each insertion scans the merged list once (O(n)), giving O(n²) total. No re-sorting. This is the version used in Section 20.

Version Edge case that forced it Enhancement added
v0None — most direct (collect, sort, merge)Re-sort + full merge each step
v_finalWasteful re-sorting — v0 re-sorts already-merged intervalsMaintain sorted invariant; each new chunk merges into its slice via 3-phase scan
Principle: Every line of complexity was earned by a specific input the previous version failed on. Here, the "failure" was wasteful re-sorting, not a wrong answer. The invariant (sorted, non-overlapping, non-adjacent) eliminates the re-sort because the list is already in merge-ready form.

11. Complexity Deep Dive

▶

Time: O(n²) — For each of n chunks, we scan the current intervals list once (O(k) where k is the current size). Total: Σk from 1 to n = O(n²). No sorting needed because the invariant keeps the list sorted.

Space: O(n) — The intervals list holds at most n intervals (if none merge). The result list holds n snapshots, each O(n), so O(n²) total for output — but this is the required output, not auxiliary space. Auxiliary space is O(n).

Why not O(n log n)? A balanced BST (e.g., Python's sortedcontainers) could give O(n log n) by finding the merge slice in O(log n). But for n ≤ 1000, the linear scan is simpler and fast enough. The BST adds complexity (custom key, rebalancing) for no practical benefit at this scale.

12. Edge Cases & Gotchas

▶
  • Adjacent intervals merge (consecutive): [1,3] and [4,6] merge into [1,6] because 4 = 3+1. Use start ≤ prev_end + 1 as the merge condition, NOT start ≤ prev_end.
  • Duplicate chunks: If [2,5] arrives again, it's fully inside [1,7] — the merge phase absorbs it (merged_right stays 7). No change to intervals.
  • Single-byte chunk: [5,5] is valid. It merges with [1,4] (consecutive) or [3,7] (overlap).
  • Snapshot copy: Use [iv[:] for iv in intervals], NOT (iv[:] for iv in intervals) (generator — not JSON serializable) and NOT intervals directly (later mutations corrupt earlier snapshots).
  • Empty chunks list: Return [] — no chunks, no snapshots.
  • Chunk fully contains existing: [1,10] after [3,5] — the merge phase absorbs [3,5] into [1,10].

13. Common Mistakes

▶
  • Forgetting the +1 (consecutive merge): Using start ≤ prev_end leaves [1,3] and [4,6] separate. The problem says "consecutive", so use start ≤ prev_end + 1.
  • Appending a generator: result.append(iv[:] for iv in intervals) creates a generator object, not a list. CodeSignal rejects it as "not JSON serializable". Always use list comprehension [...].
  • Not copying snapshots: result.append(intervals) appends a reference. Later mutations change all snapshots. Use [iv[:] for iv in intervals] for a deep copy.
  • Re-sorting every time (v0 trap): Works but O(n² log n). The invariant makes sorting unnecessary — the list is already sorted.

14. Flashcards

▶
Q: What is the merge condition for "consecutive" intervals?

start ≤ prev_end + 1. The +1 captures adjacency: [1,3] and [4,6] merge because 4 ≤ 3+1. Without the +1, they'd stay separate.

Q: Why append [iv[:] for iv in intervals] instead of intervals?

To snapshot the current state. If you append intervals directly, later mutations (new chunks merging) corrupt all earlier snapshots. iv[:] copies each interval; the list comprehension creates a new list.

Q: What is the time complexity of the optimal solution?

O(n²) — each of n chunks scans the current interval list once (O(k)). Total: Σk = O(n²). No sorting because the invariant keeps the list sorted.

Q: What's the invariant maintained by intervals?

Sorted by start, non-overlapping, non-adjacent. This means each new chunk only affects a contiguous slice — the intervals that overlap or touch it. No need to re-sort.

Q: What happens with a duplicate chunk?

It's absorbed in the merge phase. merged_right doesn't grow (the duplicate is inside the existing range), so intervals stays the same. The snapshot is identical to the previous one.

15. Where It Is Used (Real World)

▶

File upload progress tracking: Exactly the problem statement. A client uploads a large file in chunks (resumable uploads, parallel chunks). The server tracks which byte ranges are received and merges them to show progress and detect completion.

Memory allocation tracking: An OS tracks allocated memory blocks. Allocations and frees create and merge ranges. The free-list is a set of non-overlapping intervals that merge when adjacent blocks are freed.

Calendar/booking systems: Tracking occupied time slots. Adjacent bookings merge into one block. Overlapping bookings (double-booking) are detected by the merge.

IP address range management: CIDR block aggregation. Overlapping or adjacent subnets merge into larger blocks.

18. Related Algorithms

▶
  • Interval merging: Combining overlapping or adjacent intervals into a normalized set. Core to scheduling, allocation, and range-tracking problems.
  • Line sweep: A related technique that sorts events (starts and ends) and sweeps left-to-right to compute overlaps, union length, etc. Useful for batch problems; overkill for streaming.
  • Incremental data structures: Maintaining an invariant under insertions (sorted set, heap, balanced BST). The key decision: how much to recompute vs. update incrementally.

19. Where This Pattern Meets System Design

▶

In a real file-upload system, this pattern tracks resumable upload progress. The client uploads chunks in parallel (possibly out of order, possibly retried). The server merges received ranges to know which bytes are done and which still need to be requested.

Scale considerations:

  • For a 100GB file with 10MB chunks, that's 10,000 chunks — O(n²) = 10&sup8; operations, borderline. A BST (O(n log n)) would be safer.
  • Persist the interval list to disk (or a database) so the server can resume after a crash. The snapshot after each chunk is the recovery point.
  • If multiple clients upload the same file (deduplication), merge their interval lists. This is a union operation on two sorted interval lists — O(n + m).
  • Distributed: shard by byte range. Each shard tracks its own intervals, and a coordinator aggregates progress. The merge is associative, so sharding is clean.

Java

import java.util.*;

public class Solution {
    public List<List<int[]>> solution(int[][] chunks) {
        List<int[]> intervals = new ArrayList<>();
        List<List<int[]>> result = new ArrayList<>();
        for (int[] chunk : chunks) {
            int left = chunk[0], right = chunk[1];
            List<int[]> newIntervals = new ArrayList<>();
            int i = 0, n = intervals.size();
            while (i < n && intervals.get(i)[1] + 1 < left) {
                newIntervals.add(intervals.get(i));
                i++;
            }
            int mergedLeft = left, mergedRight = right;
            while (i < n && intervals.get(i)[0] <= mergedRight + 1) {
                mergedLeft = Math.min(mergedLeft, intervals.get(i)[0]);
                mergedRight = Math.max(mergedRight, intervals.get(i)[1]);
                i++;
            }
            newIntervals.add(new int[]{mergedLeft, mergedRight});
            while (i < n) {
                newIntervals.add(intervals.get(i));
                i++;
            }
            intervals = newIntervals;
            List<int[]> snapshot = new ArrayList<>();
            for (int[] iv : intervals) snapshot.add(iv.clone());
            result.add(snapshot);
        }
        return result;
    }
}

21. Follow-Up Questions

▶
  • What if n is very large (10&sup6;)? O(n²) is too slow. Use a balanced BST (sortedcontainers in Python, std::set in C++) to find the merge slice in O(log n), giving O(n log n).
  • What if you need to support deletion (chunk removal)? Harder — you'd need to split merged intervals. A segment tree or interval tree with lazy propagation would work.
  • What if chunks arrive out of order? The solution handles this — the three-phase scan works regardless of where the new chunk falls in the sorted list.
  • What if you need to query "is byte X received?" Binary search the intervals list for the interval containing X. O(log n) per query.
