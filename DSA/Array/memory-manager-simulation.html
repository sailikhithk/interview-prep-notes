Memory Manager Simulation

First-fit allocator · Array + Hash Map · Time O(n·q) · Space O(k)

1. Problem Statement

Implement solution(memory, queries) for a memory manager simulation. memory starts as an array of 0s and 1s, where 0 = free and 1 = occupied. Queries are of two types:

  • •[0, x] (alloc): Allocate the leftmost block of x consecutive free units. Mark them with a unique allocation ID (starting from 1, increasing per successful allocation). Return the starting index, or -1 if impossible.
  • •[1, id] (erase): Erase the block with that allocation ID. Free all its units. Return the block length, or -1 if that ID doesn't exist or was already erased.

Return the result (list of integers) for every query.

Example:

memory = [0,1,0,0,0,1,0,0], queries = [[0,2], [0,2], [1,1], [0,3], [1,3]]

[0,2] → alloc 2 at index 0 (memory[0,1] become ID 1) → 0. [0,2] → alloc 2 at index 3 (memory[3,4] become ID 2) → 3. [1,1] → erase ID 1, free memory[0,1], return length 2. [0,3] → alloc 3 at index 0 (memory[0,1,2] become ID 3) → 0. [1,3] → erase ID 3, return 3. Result: [0, 3, 2, 0, 3].

2. Pattern Recognition

▶

Signal words: "leftmost block of x consecutive free units", "unique allocation ID", "erase the block with that ID", "return the result for every query". This is a first-fit memory allocator — the OS classic. The array is the memory, queries are alloc/free calls.

When to reach for this pattern: Whenever a problem asks you to maintain a mutable array under "find contiguous free space" and "mark/release" operations. The key insight is that the array itself is the source of truth for occupancy, and a hash map tracks allocation metadata for O(1) erase.

Key insight: Two data structures work together: (1) the memory array (source of truth for what's free/occupied), and (2) an active_allocations dict mapping id → (start, size) for O(1) erase. Without the dict, erase would require scanning the array to find the block.

  • "Leftmost consecutive free block" → first-fit, linear scan with run-length tracking
  • "Unique allocation ID" → increment a counter on each successful alloc
  • "Erase by ID" → hash map from ID to (start, size) for O(1) lookup
  • Initial 1s are pre-occupied, NOT allocation ID 1 — they're not erasable

Approaches considered before settling on first-fit + hash map:

3. Pattern Blueprint

▶
  • 1Initialize next_alloc_id = 1 and active_allocations = {} (dict: id → (start, size)).
  • 2For each [query_type, value] in queries:
  • 3If alloc (type 0): Scan memory for the leftmost run of value consecutive 0s. If found, fill with next_alloc_id, store in dict, increment ID, append start index. Else append -1.
  • 4If erase (type 1): Look up value in active_allocations. If found, free the block (set cells to 0), remove from dict, append size. Else append -1.
  • 5Return results list.

4. How to Think About It

▶

The key insight is that the memory array is the source of truth. You don't need a separate free-list or bitmap — the array already tells you what's free (0) and what's occupied (nonzero). The alloc operation scans the array for the leftmost run of zeros; the erase operation sets cells back to 0.

The allocation ID trick is what makes erase efficient. When you alloc, you write the ID into the memory cells (not just 1). This way, each allocated block is uniquely identifiable in the array. But to erase by ID, you need to know where the block is — that's what the active_allocations dict provides: id → (start, size).

The leftmost requirement is what makes this "first-fit" (as opposed to "best-fit" or "worst-fit"). First-fit is the simplest allocator: take the first free block that's big enough. It's fast and tends to preserve large free blocks at the end (though it can cause external fragmentation at the front — a tradeoff the problem doesn't ask you to worry about).

The initial 1s in memory are pre-occupied cells (like OS kernel memory). They are NOT allocation ID 1 — they're just "occupied, not erasable". The allocation IDs start from 1 and increment only on successful allocs. If you confuse initial 1s with allocation ID 1, you'll try to erase cells that were never allocated, and get the wrong answer.

5. Real-World Analogy

▶

Parking lot allocator: A parking lot with N spots (the memory array). Some spots are permanently reserved (initial 1s). Cars arrive and need x consecutive spots. The attendant parks them in the leftmost available run of x spots and gives them a ticket with a unique ID.

When a car leaves (erase by ID), the attendant looks up the ticket ID, finds where they parked (start, size), frees those spots, and reports how many spots were freed. If someone tries to leave with a fake ticket (ID not in the dict), the attendant says "no such car" (-1).

Mapping:

  • memory array = parking spots (0 = empty, nonzero = occupied with ticket ID)
  • alloc [0, x] = "I need x consecutive spots" → park in leftmost run
  • erase [1, id] = "Car with ticket id is leaving" → free their spots
  • active_allocations dict = the attendant's ticket ledger (ID → spot, count)
  • initial 1s = permanently reserved spots (not ticketed, not freeable)

8. How It Works (Step by Step)

▶
1Initialize: next_alloc_id = 1, active_allocations = {}, results = [].
2For each query: Destructure as [query_type, value].
3Alloc (type 0): Call find_leftmost_free_block(value) — a linear scan tracking the current run of zeros. If a run of length value is found, return its start index; else return -1.
4If start_index == -1: append -1 to results, continue. Else: fill memory[start_index : start_index + value] with next_alloc_id, store (start_index, value) in the dict, increment next_alloc_id, append start_index.
5Erase (type 1): Look up value in active_allocations. If not found, append -1. Else: get (start, size), set memory[start : start + size] back to 0, remove the ID from the dict, append size.
6Return results.

The find_leftmost_free_block helper is the heart of alloc: it scans once, tracking run_start and run_length. When run_length == block_size, return run_start. If a 1 is hit, reset run_length = 0. This is O(n) per alloc.

10. From Brute Force to Optimal — Every Decision & Why

▶

v0 — Brute Force: scan + erase without dict

Time: O(n·q) alloc, O(n) erase-by-scan Space: O(1) 
def solution_bruteforce(memory, queries):
    result = []
    next_id = 1
    allocations = {}
    for query_type, value in queries:
        if query_type == 0:
            # Scan for leftmost run of 'value' zeros
            run_start = 0
            run_len = 0
            found = -1
            for i in range(len(memory)):
                if memory[i] == 0:
                    if run_len == 0:
                        run_start = i
                    run_len += 1
                    if run_len == value:
                        found = run_start
                        break
                else:
                    run_len = 0
            if found == -1:
                result.append(-1)
                continue
            alloc_id = next_id
            next_id += 1
            for i in range(found, found + value):
                memory[i] = alloc_id
            allocations[alloc_id] = (found, value)
            result.append(found)
        else:
            alloc_id = value
            if alloc_id not in allocations:
                result.append(-1)
                continue
            start, size = allocations.pop(alloc_id)
            for i in range(start, start + size):
                memory[i] = 0
            result.append(size)
    return result

Flaw: This is actually already quite good — it uses the dict for erase. The "brute force" aspect is the O(n) linear scan for alloc, which can't be avoided without a segment tree. But the code is verbose: the alloc scan is inline, making it hard to read. No helper function.

v_final — Clean solution with helper function

Time: O(n·q) Space: O(k) 
def solution(memory, queries):
    results = []
    next_allocation_id = 1
    active_allocations = {}
    n = len(memory)

    def find_leftmost_free_block(block_size):
        run_start = 0
        run_length = 0
        for i in range(n):
            if memory[i] == 0:
                if run_length == 0:
                    run_start = i
                run_length += 1
                if run_length == block_size:
                    return run_start
            else:
                run_length = 0
        return -1

    for query_type, value in queries:
        if query_type == 0:
            start_index = find_leftmost_free_block(value)
            if start_index == -1:
                results.append(-1)
                continue
            allocation_id = next_allocation_id
            next_allocation_id += 1
            for i in range(start_index, start_index + value):
                memory[i] = allocation_id
            active_allocations[allocation_id] = (start_index, value)
            results.append(start_index)
        else:
            allocation_id = value
            if allocation_id not in active_allocations:
                results.append(-1)
                continue
            start_index, block_size = active_allocations.pop(allocation_id)
            for i in range(start_index, start_index + block_size):
                memory[i] = 0
            results.append(block_size)
    return results

Why final: Same O(n·q) time, but the find_leftmost_free_block helper separates the scan logic from the alloc logic, making each readable. Clear variable names (start_index, block_size, active_allocations). This is the version used in Section 20.

The helper function doesn't change the complexity — it makes the code maintainable. In an interview, clean code IS the optimization: fewer bugs, faster to explain, easier to extend.

11. Complexity Deep Dive

▶

Time: O(n · q) — Each alloc scans the memory array once (O(n)). Each erase is O(size) to zero out the cells. With q queries, worst case is O(n · q) (all allocs). The problem explicitly allows O(n² · q), so this is well within bounds.

Space: O(k) — The active_allocations dict holds at most k entries, where k is the number of active allocations. The memory array is modified in place (not copied), so no extra O(n) space.

Why not O(log n) per alloc? A segment tree tracking max-free-run per segment could find the leftmost valid block in O(log n). But implementing it correctly in an interview is very hard (lazy propagation, merge logic). The problem's O(n²·q) bound makes the linear scan sufficient. A senior should mention the segment tree as the "production" answer but implement the simple version first.

12. Edge Cases & Gotchas

▶
  • Initial 1s are NOT allocation ID 1: The initial 1s in memory are pre-occupied cells. They are not erasable. Allocation IDs start from 1 and increment only on successful allocs. Do not confuse the initial 1s with allocation ID 1.
  • Increment ID only on success: If an alloc fails (not enough contiguous space), do NOT increment next_alloc_id. IDs must be unique per successful allocation.
  • Erase a non-existent ID: If the ID isn't in active_allocations (never allocated or already erased), return -1. Do NOT throw an error.
  • Double erase: If ID 1 is erased, then erased again, the second erase returns -1 (ID 1 was removed from the dict on the first erase).
  • Alloc size larger than memory: If x > len(memory), the scan finds no run of that length, return -1.
  • Alloc size 0: Edge case — a run of 0 zeros is "found" at index 0 immediately. The problem likely won't test this, but handle it: if block_size == 0, return 0 (or -1, depending on interpretation).
  • Leftmost requirement: Must find the FIRST (leftmost) run of sufficient length, not any run. The linear scan with run_start tracking naturally gives leftmost.

13. Common Mistakes

▶
  • Incrementing ID on failed alloc: next_alloc_id += 1 before checking if the alloc succeeded. This wastes IDs and breaks uniqueness. Only increment on success.
  • Returning allocation ID instead of start index: The problem says "return the starting index" for alloc. Not the ID. Read carefully.
  • Not removing erased IDs from the dict: If you forget active_allocations.pop(alloc_id), a second erase of the same ID will return the size again (wrong — should be -1).
  • Treating initial 1s as allocation ID 1: Trying to erase ID 1 when no alloc has happened. The initial 1s are not in the dict, so erase returns -1 (correct), but some candidates try to scan for cells with value 1 and free them — wrong.
  • Not resetting run_length on hitting a nonzero cell: The scan must reset run_length = 0 when it hits a nonzero cell. Forgetting this gives false positives (counts occupied cells as part of the free run).

14. Flashcards

▶
Q: What are the two data structures and their roles?

(1) The memory array — source of truth for occupancy (0 = free, nonzero = alloc ID). (2) The active_allocations dict — maps alloc ID to (start, size) for O(1) erase lookup.

Q: When do you increment next_alloc_id?

Only on a successful alloc. If the alloc fails (not enough contiguous space), do NOT increment. IDs must be unique per successful allocation.

Q: What does alloc return? What does erase return?

Alloc returns the start index (or -1 if no space). Erase returns the block size (or -1 if ID not found). Not the allocation ID — read the problem carefully.

Q: Are the initial 1s in memory erasable?

No. The initial 1s are pre-occupied cells (like OS kernel memory). They are NOT allocation ID 1 — they're just "occupied, not in the dict". Erase only works on IDs that were created by a successful alloc.

Q: How do you find the leftmost run of x free cells?

Linear scan with run_start and run_length tracking. When memory[i] == 0, extend the run. When run_length == x, return run_start. If a nonzero cell is hit, reset run_length = 0. O(n) per alloc.

Q: What happens on a double erase (same ID twice)?

First erase: look up ID in dict, free the block, remove from dict, return size. Second erase: ID no longer in dict, return -1. The pop on the first erase is what prevents the double-free.

15. Where It Is Used (Real World)

▶

OS memory allocators: This IS the classic first-fit allocator. Real OS allocators (malloc, jemalloc) use more sophisticated variants (segregated free lists, slab allocators) but the core idea is the same: find a free block, mark it allocated, track it for later free.

Disk space allocation: File systems track free blocks with bitmaps or free lists. Allocating a file = finding consecutive free blocks. Deleting = marking them free. The bitmap is the "memory array".

Resource reservation systems: Hotel rooms, parking spots, server capacity — any system where you reserve a contiguous block of resources and release them later. The "leftmost" requirement maps to "assign the first available slot".

Container orchestration: Kubernetes scheduling: find a node with enough contiguous resources (CPU, memory). The scheduler scans nodes (the "memory array") for a fit. Simpler schedulers use first-fit; advanced ones use bin-packing.

18. Related Algorithms

▶
  • First-fit allocation: The simplest allocator strategy — take the first free block that fits. Fast but can cause external fragmentation.
  • Best-fit / worst-fit: Alternative strategies. Best-fit finds the smallest free block that fits (less waste, slower scan). Worst-fit finds the largest (leaves big blocks for future allocs).
  • Buddy allocator: Power-of-2 block sizes with recursive splitting/coalescing. O(log n) alloc/erase. Used in Linux kernel for physical page allocation.
  • Slab allocator: Pre-allocated pools for fixed-size objects. O(1) alloc/erase for common sizes. Used in Linux kernel for inode/task_struct allocation.

19. Where This Pattern Meets System Design

▶

In a real system, this pattern is the memory allocator — the foundation of every heap allocation. Real allocators (glibc malloc, jemalloc, tcmalloc) use segregated free lists (bins by size class) for O(1) alloc for common sizes, falling back to first-fit for large allocations.

Scale considerations:

  • For n = 10&sup6; (1M memory cells), O(n) per alloc is 1ms — acceptable for q < 1000. For q = 10&sup6;, you'd need the segment tree (O(q log n)).
  • Fragmentation: first-fit causes external fragmentation over time (small free blocks scattered). A compaction pass (defragment) can merge them, but it requires moving allocated blocks (updating all pointers) — expensive.
  • Concurrency: real allocators use locks or per-thread arenas. This problem is single-threaded, but a production allocator must handle concurrent alloc/erase.
  • Persistence: if the memory state must survive crashes, persist the array and dict to disk (or reconstruct the dict from the array on startup by scanning for unique IDs).

Java

import java.util.*;

public class Solution {
    public List<Integer> solution(int[] memory, int[][] queries) {
        List<Integer> results = new ArrayList<>();
        int nextAllocationId = 1;
        Map<Integer, int[]> activeAllocations = new HashMap<>();
        int n = memory.length;

        for (int[] query : queries) {
            int queryType = query[0], value = query[1];
            if (queryType == 0) {
                int startIndex = findLeftmostFreeBlock(memory, value, n);
                if (startIndex == -1) {
                    results.add(-1);
                    continue;
                }
                int allocationId = nextAllocationId++;
                for (int i = startIndex; i < startIndex + value; i++) {
                    memory[i] = allocationId;
                }
                activeAllocations.put(allocationId, new int[]{startIndex, value});
                results.add(startIndex);
            } else {
                int allocationId = value;
                if (!activeAllocations.containsKey(allocationId)) {
                    results.add(-1);
                    continue;
                }
                int[] block = activeAllocations.remove(allocationId);
                int startIndex = block[0], blockSize = block[1];
                for (int i = startIndex; i < startIndex + blockSize; i++) {
                    memory[i] = 0;
                }
                results.add(blockSize);
            }
        }
        return results;
    }

    private int findLeftmostFreeBlock(int[] memory, int blockSize, int n) {
        int runStart = 0, runLength = 0;
        for (int i = 0; i < n; i++) {
            if (memory[i] == 0) {
                if (runLength == 0) runStart = i;
                runLength++;
                if (runLength == blockSize) return runStart;
            } else {
                runLength = 0;
            }
        }
        return -1;
    }
}

#include <vector>
#include <unordered_map>

class Solution {
public:
    std::vector<int> solution(std::vector<int>& memory, std::vector<std::vector<int>>& queries) {
        std::vector<int> results;
        int next_allocation_id = 1;
        std::unordered_map<int, std::pair<int,int>> active_allocations;
        int n = memory.size();

        for (auto& query : queries) {
            int query_type = query[0], value = query[1];
            if (query_type == 0) {
                int start_index = findLeftmostFreeBlock(memory, value, n);
                if (start_index == -1) {
                    results.push_back(-1);
                    continue;
                }
                int allocation_id = next_allocation_id++;
                for (int i = start_index; i < start_index + value; i++) {
                    memory[i] = allocation_id;
                }
                active_allocations[allocation_id] = {start_index, value};
                results.push_back(start_index);
            } else {
                int allocation_id = value;
                auto it = active_allocations.find(allocation_id);
                if (it == active_allocations.end()) {
                    results.push_back(-1);
                    continue;
                }
                int start_index = it->second.first;
                int block_size = it->second.second;
                active_allocations.erase(it);
                for (int i = start_index; i < start_index + block_size; i++) {
                    memory[i] = 0;
                }
                results.push_back(block_size);
            }
        }
        return results;
    }

private:
    int findLeftmostFreeBlock(std::vector<int>& memory, int block_size, int n) {
        int run_start = 0, run_length = 0;
        for (int i = 0; i < n; i++) {
            if (memory[i] == 0) {
                if (run_length == 0) run_start = i;
                run_length++;
                if (run_length == block_size) return run_start;
            } else {
                run_length = 0;
            }
        }
        return -1;

21. Follow-Up Questions

▶
  • Can you do better than O(n) per alloc? Yes — a segment tree tracking max-free-run per segment can find the leftmost valid block in O(log n). But it's complex to implement. For the stated bound, linear scan is sufficient.
  • What about fragmentation? First-fit causes external fragmentation over time. A compaction pass can merge adjacent free blocks, but it requires moving allocated blocks (updating all pointers). In practice, allocators use segregated free lists (bins by size class) to mitigate.
  • What if queries can also "resize" an allocation? Add a third query type: [2, id, new_size]. Resize in place if the adjacent space is free; else allocate a new block, copy, and free the old one. This is how realloc works.
  • What if memory is very large (10&sup9;)? Can't store it as an array. Use a free-list of intervals (sorted by start). Alloc splits a free interval; erase merges freed space back (checking for adjacent free intervals to coalesce). O(n) per operation where n is the number of free intervals.

22. Quick Reference

▶

One-line summary: First-fit allocator. Array = source of truth (0=free, nonzero=alloc ID). Dict = ID→(start,size) for O(1) erase. Alloc: linear scan for leftmost run of free cells. Erase: dict lookup + zero cells. O(n·q) time, O(k) space.

def solution(memory, queries):
    res, nid, allocs = [], 1, {}
    for qt, val in queries:
        if qt == 0:
            rs, rl, found = 0, 0, -1
            for i in range(len(memory)):
                if memory[i] == 0:
                    if rl == 0: rs = i
                    rl += 1
                    if rl == val: found = rs; break
                else: rl = 0
            if found == -1: res.append(-1); continue
            for i in range(found, found+val): memory[i] = nid
            allocs[nid] = (found, val); nid += 1; res.append(found)
        else:
            if val not in allocs: res.append(-1); continue
            s, sz = allocs.pop(val)
            for i in range(s, s+sz): memory[i] = 0
            res.append(sz)
    return res
