4. High-Level Design (HLD)

Three lanes: edge (auth + idempotency), core (state machine + ledger, one ACID tx), async (PSP call, webhooks, reconciliation). The core lane never calls the PSP synchronously — it writes intent + outbox and returns.

5. Read & Write Data Flow Traces

Write Flow (charge)

  1. Client POST /charges with idempotency key
  2. Gateway auth + rate limit
  3. Payment Service checks idempotency store
  4. If key exists → return cached response
  5. Else BEGIN TX: insert payment row (PENDING) + debit + credit + outbox row
  6. COMMIT — return 202 Accepted with payment_id
  7. Outbox relay publishes to Kafka
  8. Worker consumes → calls PSP → updates state
  9. Webhook from PSP → update state (AUTHORIZED/DECLINED)

Read Flow (status)

  1. Client GET /charges/{id}
  2. Gateway auth
  3. Payment Service reads from read replica
  4. If state is terminal → return
  5. If PENDING > 30s → query PSP adapter
  6. Cache result in Redis (TTL 60s)
  7. Return state + ledger summary

6. Core Entities & Database Schema

PostgreSQL for ledger (ACID is the product). DynamoDB for idempotency keys (TTL native). Redis for hot cache.

  id            UUID PRIMARY KEY,
  merchant_id   UUID NOT NULL,
  amount_cents  BIGINT NOT NULL,
  currency      CHAR(3) NOT NULL,
  state         VARCHAR(20) NOT NULL,  -- PENDING|AUTHORIZED|CAPTURED|SETTLED|DECLINED|REFUNDED

) PARTITION BY RANGE (created_at);

ledger_entries (
  id            BIGSERIAL PRIMARY KEY,
  payment_id    UUID NOT NULL REFERENCES payments(id),
  account_id    UUID NOT NULL,
  debit_cents   BIGINT NOT NULL DEFAULT 0,
  credit_cents  BIGINT NOT NULL DEFAULT 0,
  version       INT NOT NULL,           -- OCC
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CHECK(debit_cents <> credit_cents),   -- one or the other
  CHECK(debit_cents >= 0 AND credit_cents >= 0)
);

outbox_events (
  id            BIGSERIAL PRIMARY KEY,
  aggregate_id  UUID NOT NULL,
  event_type    VARCHAR(50) NOT NULL,
  payload       JSONB NOT NULL,
  status        VARCHAR(20) NOT NULL DEFAULT 'PENDING',
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  published_at  TIMESTAMPTZ
);

accounts (
  id            UUID PRIMARY KEY,
  merchant_id   UUID NOT NULL,
  type          VARCHAR(20) NOT NULL,   -- ASSET|LIABILITY|EQUITY|REVENUE|EXPENSE
  balance_cents BIGINT NOT NULL DEFAULT 0  -- derived, not source of truth
);

Partition payments by created_at (monthly). Shard ledger_entries by merchant_id. Balance is derived via SUM, cached in accounts table, reconciled nightly.

Java — Idempotent Payment Service

@Service
@Transactional
public class PaymentService {
    private final PaymentRepository payments;
    private final LedgerRepository ledger;
    private final OutboxRepository outbox;

    public ChargeResponse charge(ChargeRequest req, String idempotencyKey) {
        // 1. Idempotency check
        Optional<Payment> existing = payments.findByIdempotencyKey(idempotencyKey);
        if (existing.isPresent()) {
            return ChargeResponse.cached(existing.get());
        }
        // 2. Create payment in PENDING
        Payment p = Payment.newPending(req, idempotencyKey);
        payments.save(p);
        // 3. Double-entry ledger (debit merchant, credit clearing)
        ledger.save(LedgerEntry.debit(p.getMerchantAccount(), req.getAmountCents()));
        ledger.save(LedgerEntry.credit(p.getClearingAccount(), req.getAmountCents()));
        // 4. Outbox event (same tx — atomic)
        outbox.save(OutboxEvent.of("PaymentRequested", p));
        // 5. COMMIT happens here (annotation-driven)
        return ChargeResponse.accepted(p);
    }
}

Python — Outbox Relay

import psycopg2, json
from kafka import KafkaProducer

producer = KafkaProducer(
    bootstrap_servers=['msk-1:9092', 'msk-2:9092'],
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

def relay_loop(conn):
    while True:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT id, aggregate_id, event_type, payload
                FROM outbox_events
                WHERE status = 'PENDING'
                ORDER BY id
                FOR UPDATE SKIP LOCKED
                LIMIT 100
            """)
            batch = cur.fetchall()
            for row in batch:
                event_id, agg_id, etype, payload = row
                producer.send('payments.requests', {
                    'event_id': event_id,
                    'aggregate_id': str(agg_id),
                    'type': etype,
                    'payload': payload
                })
                cur.execute(
                    "UPDATE outbox_events SET status='PUBLISHED', published_at=NOW() WHERE id=%s",
                    (event_id,)
                )
        conn.commit()
        time.sleep(0.5)  # poll interval

14. Resiliency & Failure Mitigations

⚡ PSP Timeout

PSP doesn't respond within 30s. Mitigation: mark payment as PENDING, retry with exponential backoff (3 attempts). If still failing, move to manual review queue. Never auto-decline — the charge may have succeeded.

⚡ Kafka Lag

Consumer can't keep up. Mitigation: alert at >10K lag, auto-scale consumers, increase partition count. Idempotent consumers mean we can scale freely.

⚡ DB Primary Down

Aurora failover (typically <30s). Mitigation: circuit breaker on writes, queue incoming requests in Kafka, replay after failover. Reads continue on replicas.

⚡ Duplicate Webhook

PSP sends same webhook twice. Mitigation: idempotency on webhook event_id, state machine rejects invalid transitions (AUTHORIZED → AUTHORIZED is no-op).

⚡ Network Partition

Split brain between regions. Mitigation: Aurora Global DB with writer in one region, regional affinity. Failover via Route 53 health checks.

⚡ Hot Merchant

One merchant dominates traffic. Mitigation: split shard by merchant_id + date, rate limit per merchant, dedicated shard for top-10 merchants.

19. Handling Interviewer Pushbacks

Q: "What if the outbox relay crashes after publishing but before marking PUBLISHED?"

"Consumers are idempotent on event_id, so a duplicate publish is harmless — they'll see the same event_id and no-op. The relay re-fetches PENDING rows on restart and republishes. At-least-once semantics, exactly-once effect."

Q: "How do you handle a hot merchant that dominates one shard?"

"Three options: (1) split the shard by merchant_id plus created_at composite key, (2) rate limit the merchant at the gateway, (3) provision a dedicated shard for top-10 merchants. I'd start with rate limiting, then split if sustained."

Q: "What if the PSP double-charges due to their own retry?"

"We send a unique request_id to the PSP on every charge. If they retry, they should use the same request_id. If they don't honor idempotency, we reconcile nightly against their settlement report and issue automatic refunds for duplicates."

Q: "Why not use TigerBeetle or a purpose-built ledger DB?"

"TigerBeetle is purpose-built for this — it's 1M TPS, ACID, append-only. If I'm greenfield and ledger-only, I'd use it. But PostgreSQL gives me flexibility: JSONB for metadata, standard SQL for reporting, mature ecosystem. At 10K TPS, Postgres is fine. At 1M TPS, I'd migrate the ledger to TigerBeetle."

Q: "How do you ensure exactly-once across the PSP and your ledger?"

"You can't — the PSP is an external system. You get at-least-once delivery with idempotent receivers. We use a state machine: PENDING → AUTHORIZED is a valid transition, AUTHORIZED → AUTHORIZED is a no-op. The idempotency key at our API plus the request_id at the PSP gives us effective exactly-once."

20. Advanced Concept Deep Dives

▶ Two-Phase Commit vs Saga

2PC is a blocking protocol — if the coordinator dies, participants are stuck. Sagas break a distributed transaction into a sequence of local ACID transactions with compensating actions. For payments, we use orchestration sagas: the payment service is the orchestrator, each step (auth, capture, settle) is a local tx, and failures trigger compensating transactions (void, refund).

Why not 2PC? PSPs don't support XA. Kafka doesn't support XA. The outbox pattern gives us the same guarantee without blocking.

▶ OCC vs Pessimistic Locking for Ledger

Optimistic Concurrency Control (OCC) uses a version column — if the version changed, retry. Pessimistic locking uses SELECT FOR UPDATE. For the ledger, we use OCC on the account balance: UPDATE accounts SET balance = balance + X, version = version + 1 WHERE id = ? AND version = ?. If 0 rows affected, retry with backoff.

Why OCC? Low contention on per-account writes, no lock held during PSP call, simpler deadlock story.

▶ Reconciliation as the Safety Net

No distributed system guarantees exactly-once across external boundaries. Reconciliation is the nightly safety net: download PSP settlement report, compare to our ledger, flag mismatches. Three categories: (1) we have it, PSP doesn't → we overcharged, refund. (2) PSP has it, we don't → we missed, create entry. (3) Amount mismatch → manual review.

SLA: 99.99% of transactions reconcile within $0.01. Anything else triggers a P2 alert.

▶ Cell-Based Architecture (Capital One)

Capital One's pattern: group services into cells, each cell is self-contained (compute, data, messaging). Shuffle-sharding assigns each merchant to a random cell. If a cell goes bad (poison pill), only its merchants are affected. Blast radius is bounded.

Why? At 99.99% availability, a single bad deploy can burn your error budget. Cells isolate failures.

▶ Idempotency Key Design

The idempotency key is a client-generated UUID v4. We store it in a unique constraint on (merchant_id, idempotency_key). On retry, the DB unique violation is caught and we return the cached response. The key must be stable across retries — clients should use a deterministic key per logical operation, not a random one per HTTP attempt.

TTL: 24h in Redis, permanent in DB (for audit). After 24h, the same key can be reused for a new logical operation — but that's a client bug.

▶ Webhook Signature Verification

PSP sends X-PSP-Signature: t=timestamp,v1= hmac_sha256(timestamp.body, secret). We verify by recomputing the HMAC with our shared secret. If valid, process. If invalid, reject with 400. Prevents webhook spoofing.

Replay protection: reject if timestamp is > 5 min old. Store processed event_ids in Redis (7 day TTL) to detect duplicates.
