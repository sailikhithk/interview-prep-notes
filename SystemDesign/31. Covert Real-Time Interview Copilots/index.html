How covert interview tools hide

An educational explainer of the architecture, evasion techniques, and defender-side detection of tools that attempt to hide from Activity Monitor and screen-share during live interviews.

DEFENSIVE FRAMING · FOR LEARNING OS INTERNALS & EDR DESIGN · NOT A HOW-TO

This document studies how covert tools work so defenders can detect them. Every technique has a corresponding detection. The "undetectable" marketing most tools advertise is snake oil on modern macOS — Apple's Hardened Runtime, SIP, Notarization, and TCC have made the high tiers of evasion extremely difficult.

The interesting engineering is on the detection side: Endpoint Security framework, ScreenCaptureKit internals, TCC audit, and keystroke biometrics. That's where the real system design lives.

01The 4-layer pipeline

Most covert interview tools share a common architecture: capture the interview content, route it through a hidden channel to an AI backend, and inject the answer back without the proctor seeing. Each layer is a separate engineering problem with its own evasion and detection surface.

Figure 1 — The 4-layer pipeline shared by most covert interview tools

The capture layer uses standard macOS APIs (CGDisplayStream, ScreenCaptureKit, AVCaptureSession) — these are documented and legitimate. The difficulty starts at layer 2: routing the captured data to an AI backend without the network monitor or proctoring agent seeing it. Layers 3 and 4 are where the real evasion engineering lives.

02Process hiding — the 5 tiers

Activity Monitor on macOS reads from launchd, the process list (proc_info syscall), and Endpoint Security framework events. Hiding a process is an escalating ladder. The higher the tier, the harder the technique — and the harder the detection.

Figure 2 — The 5 tiers of process hiding. Higher = harder to build, but also harder to detect.

Tier 1 — Cosmetic (what most "undetectable" tools actually do)

Name spoofing: rename the binary to com.apple.audiohelperd or GoogleUpdaterHelper. Activity Monitor shows the name, not the code-signing identity. Bundle ID mimicry: set CFBundleIdentifier to com.apple.something.*. Detection: codesign -dv, entitlement audit, path verification. Trivially caught by any EDR.

Tier 2 — Persistence blending

Install a LaunchAgent in ~/Library/LaunchAgents alongside 50+ legitimate agents (Slack, Zoom, Dropbox all run agents). Or register via SMAppService (macOS 13+) — shows in Settings → General → Login Items, but users rarely audit. Detection: launchctl list | grep -v com.apple, sfltool dumpbtm (Background Task Manager dump).

Tier 3 — Process injection (the real hiding, and the focal point)

DYLD_INSERT_LIBRARIES: inject a dylib into a legitimate process (Slack, Chrome). Your code runs inside Slack's PID — Activity Monitor shows "Slack," not your tool. Mitigated on macOS by Hardened Runtime + Library Validation (signed-binary-only loading). Apple-signed apps can't be DYLD-injected since ~2019. Workaround: inject into unsigned or ad-hoc-signed helper processes, or processes with com.apple.security.cs.disable-library-validation entitlement. Mach task port hijack: task_for_pid on a target — requires SIP disabled or com.apple.security.cs.debugger entitlement. Method swizzling: once injected, hook NSApplication to hide windows from CGWindowListCreateImage.

Tier 4 — Kernel-level (mostly dead on modern macOS)

KEXT (kernel extension): old way to filter proc_info syscalls and lie to ps. Requires reboot, kext consent, deprecated for non-Apple developers since macOS 11. Detection: kextstat, kmutil showloaded. Apple killed third-party kexts in macOS 12+; you'd need a System Extension now, which is visible.

Tier 5 — Hardware / firmware (out of scope)

DMA attacks via Thunderbolt, SPI flash implants. Not what interview-cheating tools do — too expensive, too risky, requires physical access. Included for completeness of the taxonomy.

Key insight: on modern macOS (SIP on, Hardened Runtime, notarization required), Tier 3+ is very hard. Most "undetectable" interview tools are Tier 1–2 only, which means any competent EDR or even a curious sysadmin catches them. The marketing oversells the reality.

03Screen-share evasion — the core trick

The interview platform runs Zoom, Teams, or Google Meet with screen-share. The tool needs to show AI output to the user without it appearing in the shared stream. This is the single most important technique, and it relies on a legitimate macOS API.

Figure 3 — How NSWindowSharingNone makes the overlay invisible to screen-share

The technique

NSWindowSharingNone: set window.sharingType = .none. This tells CoreGraphics "don't include this window in CGWindowListCreateImage." Zoom's screen-share uses CGDisplayStream or ScreenCaptureKit, which respects this flag. The overlay is visible to the user, invisible to the proctor. This is the #1 technique — and it's a legitimate API (used by DRM apps, screen-recording tools, banking apps).

Transparent overlay: window.backgroundColor = .clear, window.opaque = false, window.level = .screenSaver (above everything). Combined with sharingType = .none.

Display reconfiguration detection: register CGDisplayRegisterReconfigurationCallback to detect when screen-share starts (display mode changes), then hide the window temporarily. CGSession notification: monitor kCGSessionConsoleConnectKey to detect AirPlay / screen-share.

The detection (defender side)

Detection 1 — Window enumeration

Call CGWindowListCopyWindowInfo(kCGWindowListOptionAll, kCGNullWindowID) and check kCGWindowSharingState for every window. Any .none window is suspicious — legitimate apps rarely use it. This is a 10-line audit script.

Detection 2 — Capture mismatch

Compare what's visible to the user (screenshot via CGDisplayCreateImage) vs. what the screen-share app receives. If they don't match, a hidden overlay exists. Proctoring platforms increasingly do this server-side.

Detection 3 — ScreenCaptureKit force-include

Hook SCStreamConfiguration to force-include all windows, ignoring sharingType. Apple can update ScreenCaptureKit to make this the default for proctoring contexts.

04The cat-and-mouse game

This is the interesting system-design framing. It's an asymmetric game between attacker (tool developer) and defender (Apple + EDR vendors + proctoring platforms). Each side has structural advantages.

Figure 4 — The asymmetric game. Apple controls the OS and can deprecate APIs; attackers only have public APIs to abuse.

Why the defender is winning (2026)

APPLE LAYER

Hardened Runtime

  • Library Validation kills DYLD injection into signed apps
  • Entitlements required for dangerous APIs
  • com.apple.security.cs.disable-library-validation rare

OS LAYER

SIP + Notarization

  • SIP prevents kernel-level hiding
  • Notarization traces binaries to a Developer ID
  • Gatekeeper blocks unsigned distribution

AUDIT LAYER

TCC + ESF

  • TCC logs every Accessibility / Screen Recording grant
  • log show --predicate 'subsystem == "com.apple.TCC"'
  • Endpoint Security framework = EDR without kexts

Where the attacker still wins

Tier 1–2 (cosmetic) against non-technical proctors. This is why most "undetectable" tools are marketed at low-tier interviews, not FAANG loop proctors who run EDR-grade detection. The economics: cheap tools target cheap interviews.

05Covert channels — the rest of the stack

Beyond process hiding and screen-share evasion, there are three more layers. Each is its own engineering domain with its own detection science.

Layer Technique Detection
Audio Ultrasonic output (>18kHz) · CoreAudio HAL tap to hidden virtual device · Bluetooth A2DP direct route to earpiece · bone-conduction system_profiler SPAudioDataType · spectral analysis of mic input · ioreg BT enumeration · physical ear inspection
Network DNS tunneling (high-entropy subdomains) · HTTPS to innocuous endpoint · WebSocket keep-alive · steganography in image pixels · domain fronting (mostly dead) TLS interception (MITM proxy) · DNS entropy analysis · flow analysis · lsof -i -nP
Input CGEventTap synthetic keystrokes · humanized timing (50–200ms jitter) · typos + corrections · paste (detected by clipboard monitor) Accessibility entitlement audit · keystroke biometrics (inter-key timing distribution too uniform) · clipboard watchers

The audio channel is the most physically detectable — proctoring services increasingly require a second camera or phone placed behind the candidate showing their ears. The network channel is the most software-detectable — TLS interception at the proctoring endpoint catches everything. The input channel is the most statistically detectable — synthetic keystrokes have a timing distribution that's too uniform even with jitter, because real humans have long-tail pauses that jitter doesn't model.

06What to study next

If you want to go deep on the system design — either to build detection (defender) or to understand the OS internals — here's the curriculum, ordered from foundational to advanced.

  • *OS Internals* trilogy — Jonathan Levin. Vol I: Userland, Vol II: Kernel, Vol III: Security. The definitive macOS internals reference. Start with Vol I if you're new to macOS internals; Vol III if you specifically want security.
  • Endpoint Security framework — Apple's EndpointSecurity.framework. How EDR works on modern macOS. Read the eslogger man page, Apple's ESF docs, and write a tiny ESF client that logs process events.
  • TCC / privacy permissions — tccutil, TCC.db schema, PrivacyPreferencesPolicyControl MDM profile. Run log show --predicate 'subsystem == "com.apple.TCC"' and watch every permission grant in real time.
  • ScreenCaptureKit — Apple's modern capture API (replaced CGDisplayStream in macOS 12.3+). Understand SCContentFilter — it's the core of the screen-share-evasion arms race. Build a tiny screen recorder.
  • Code signing + notarization — codesign, spctl, notarytool. Understand why Tier 3 attacks are hard now: sign a binary, notarize it, then try to DYLD-inject into it.
  • MITRE ATT&CK for macOS — the canonical taxonomy. Techniques T1564 (Hide Artifact), T1547 (Boot/Logon Autostart), T1055 (Process Injection) — all mapped to macOS specifics. Read the technique pages, then find them on your own machine.
  • Conference talks — DEF CON, Black Hat, OBTS (Objective by the Sea — macOS-specific security conference). Many talks on process hiding and detection. Start with OBTS talks on YouTube.
