5. Read & Write Data Flow Traces

Online Scoring Flow

  1. Card swipe → Kafka topic (partition by card BIN)
  2. Flink consumer computes velocity features (1m, 1h, 24h windows)
  3. Redis lookup: card history, merchant risk, geo pattern
  4. XGBoost model scores (0-1 fraud probability)
  5. Decision engine: rules first (hard decline), then ML fusion
  6. If score > 0.9 → decline + alert. 0.3-0.9 → review. <0.3 → approve
  7. Decision sent to auth system in <67ms

Feedback & Retrain Flow

  1. Agent reviews flagged transactions in UI
  2. Agent labels: true fraud or false positive
  3. Labeled data written to S3 (partitioned by date)
  4. Nightly Spark job joins labels with features
  5. Retrain XGBoost on 30-day window + labeled data
  6. Model registered to MLflow with version + metrics
  7. Shadow deploy: new model runs in parallel, compare scores
  8. Promote if FPR and FNR both improve by >1%

9. Partitioning & Database Scaling

Kafka: Partition by card BIN

  • Why — preserves card-level ordering
  • 128 partitions — 50K TPS / 128 ≈ 390 TPS/partition
  • Consumer group — one Flink task per partition
  • Hot card — rare, but split via sub-partition

Redis: Shard by card_id

  • 10 shards — 20M cards/shard, 20GB/shard
  • Consistent hashing — minimal reshuffle on scale
  • Read replica — 1 replica per shard for reads
  • Eviction — TTL 24h, LRU for overflow

10. Consistent Hashing & Ring Mechanics

Redis cluster uses 16384 hash slots. Each card_id maps to a slot via CRC16. Slots are assigned to shards. Resharding moves slots without rehashing all keys.

Java — Flink Feature Processor

public class FraudFeatureProcessor extends ProcessFunction<Transaction, ScoredTxn> {
    private transient RedisClient redis;
    private transient XGBoostModel model;

    @Override
    public void open(Configuration cfg) {
        redis = RedisClient.create("redis://fraud-cluster:6379");
        model = XGBoostModel.load("/models/fraud_v2.3.1.json");
    }

    @Override
    public void processElement(Txn txn, Context ctx, Collector<ScoredTxn> out) {
        // 1. Compute velocity from Flink state
        VelocityState state = getRuntimeContext().getState(velocityDesc);
        long count1m = state.incrementAndGet(txn.getTimestamp());

        // 2. Fetch card history from Redis
        CardFeatures hist = redis.get("card_features:" + txn.getCardId());

        // 3. Build feature vector
        float[] features = buildFeatures(txn, count1m, hist);

        // 4. Score
        float score = model.predict(features);

        // 5. Decide
        String decision = decisionEngine.decide(score, txn, hist);

        // 6. Update Redis (async)
        redis.asyncSet("card_features:" + txn.getCardId(), hist.updated(txn));

        out.collect(new ScoredTxn(txn, score, decision));
    }
}

Python — Decision Engine

from enum import Enum
from dataclasses import dataclass

class Decision(str, Enum):
    APPROVE = "approve"
    REVIEW = "review"
    DECLINE = "decline"

@dataclass
class DecisionEngine:
    decline_threshold: float = 0.9
    review_threshold: float = 0.3

    def decide(self, score: float, txn: dict, hist: dict) -> Decision:
        # Rules first (hard declines — fast, explainable)
        if self._hard_decline(txn, hist):
            return Decision.DECLINE
        # ML fusion
        if score >= self.decline_threshold:
            return Decision.DECLINE
        if score >= self.review_threshold:
            return Decision.REVIEW
        return Decision.APPROVE

    def _hard_decline(self, txn: dict, hist: dict) -> bool:
        # Impossible travel: > 1000km in < 5 min
        if hist.get("last_geo") and self._distance(hist["last_geo"], txn["geo"]) > 1000:
            if txn["timestamp"] - hist["last_ts"] < 300:
                return True
        # Velocity: > 10 txn in 1 min
        if hist.get("velocity_1m", 0) > 10:
            return True
        # Amount: > 10x average
        if hist.get("avg_amount") and txn["amount_cents"] > 10 * hist["avg_amount"]:
            return True
        return False

    def _distance(self, geo1: str, geo2: str) -> float:
        # Haversine simplified
        lat1, lon1 = map(float, geo1.split(","))
        lat2, lon2 = map(float, geo2.split(","))
        return ((lat2 - lat1)**2 + (lon2 - lon1)**2) ** 0.5 * 111

14. Resiliency & Failure Mitigations

⚡ Model Inference Timeout

XGBoost exceeds 30ms. Mitigation: return cached score from Redis (last known good). If no cache, default to 0.0 (approve) — fail open for latency, catch in reconciliation.

⚡ Redis Down

Feature store unavailable. Mitigation: Flink state has 1m window in memory. For 24h history, degrade to rules-only mode. Alert P1.

⚡ Flink Checkpoint Failure

Checkpoint to S3 fails. Mitigation: retain old checkpoint, retry with backoff. If 3 consecutive failures, restart from last good checkpoint. Unprocessed events replayed from Kafka (7d retention).

⚡ Model Regression

New model has worse FPR. Mitigation: shadow mode for 24h, compare metrics. Auto-rollback if FPR degrades >10%. MLflow keeps last 5 versions.

⚡ Kafka Partition Hotspot

One card BIN dominates. Mitigation: sub-partition by card_id within BIN. Or rekey by card_id (loses BIN ordering but balances load).

⚡ Feedback Label Delay

Agents take 48h to label. Mitigation: train on 30-day window with labels, accept delay. Use active learning — prioritize borderline cases for agents.

19. Handling Interviewer Pushbacks

Q: "What if the model gives a wrong score — how do you explain a decline to the customer?"

"We log SHAP values for every declined transaction. The agent sees the top 5 contributing features — e.g., 'amount 10x average', 'velocity 8 in 1 min', 'geo mismatch'. The customer gets a reason code. This is both a regulatory requirement (fair lending) and a trust requirement."

Q: "How do you handle concept drift — fraud patterns change?"

"Three signals: (1) FPR/FNR drift in production metrics, (2) feature distribution drift via KS test on incoming features vs training, (3) agent feedback volume spike. Any of these triggers an out-of-cycle retrain. We also retrain nightly regardless. The 30-day training window adapts to recent patterns."

Q: "Why not use deep learning for better accuracy?"

"Two reasons: (1) latency — XGBoost is <30ms, a decent LSTM is 100ms+. (2) explainability — SHAP works on tree models, deep learning requires LIME or attention which is less precise. If I had more latency budget (batch scoring), I'd use a sequence model for transaction history. For real-time, XGBoost is the right trade."

Q: "What if a fraudster adapts to your rules?"

"Rules are the first line — fast and explainable but rigid. ML is the second line — adaptive but slower. If fraudsters adapt to rules, the ML model catches the residual pattern. We also run adversarial testing: red team tries to evade the model, we retrain on their attempts. It's a cat-and-mouse game; the feedback loop is how we stay ahead."

Q: "How do you ensure 99.99% availability with a 100ms SLA?"

"Fail open on latency — if any component times out, approve the transaction and catch it in post-transaction review. The fraud rate is 0.1%, so approving everything costs 0.1% of transactions in fraud loss. The SLA is for the legitimate 99.9% — they should never be blocked by our latency. We'd rather eat fraud than block good customers."

20. Advanced Concept Deep Dives

▶ Feature Store Architecture (Online vs Offline)

Two-tier feature store: online (Redis, sub-ms, last 24h, hot features) and offline (S3 + Parquet, Spark-queryable, years of history, for training). The offline store is the source of truth; the online store is a projection. Feast or Tecton can manage the sync.

Challenge: training-serving skew. The online features must match what training used. We log every feature vector used in scoring to S3, so training can replay exact features.

▶ Shadow Mode & Model Promotion

New model runs in parallel — receives the same features, produces a score, but the score is logged not acted upon. After 24h, compare: (1) FPR on legitimate txn, (2) FNR on known fraud, (3) score distribution shift. If FPR and FNR both improve by >1% and distribution shift is <5%, promote. Otherwise, iterate or abandon.

Why 24h? Captures daily patterns (morning rush, evening dining, weekend spikes).

▶ Geo-Velocity Feature (Impossible Travel)

Track last transaction geo + timestamp per card. On new txn, compute Haversine distance. If distance / time_diff > 1000 km/h (faster than commercial flight), flag as impossible travel. Edge cases: airplane Wi-Fi purchases (legit but geo jumps), timezone bugs (use UTC always).

Implementation: store last_geo + last_ts in Redis. Flink computes the feature. Use coarse geo (0.1° ~ 11km) to avoid GPS jitter.

▶ Active Learning for Feedback Efficiency

Agents can't review every transaction. Active learning prioritizes borderline cases (score 0.3-0.7) for agent review — these are the most informative labels. Clear approves and clear declines are auto-labeled. This reduces agent load by 80% while improving model quality faster.

▶ Explainability (SHAP vs LIME)

SHAP (SHapley Additive exPlanations) gives exact feature contributions for tree models. LIME is approximate but model-agnostic. For XGBoost, SHAP is the standard — it's fast (TreeSHAP algorithm) and precise. Every declined transaction gets a SHAP plot in the agent UI and a reason code for the customer.

Regulatory: Fair lending laws require explainable declines. SHAP satisfies this.

▶ Flink Exactly-Once with Kafka

Flink's exactly-once uses (1) Kafka source with committed offsets in Flink checkpoints, (2) Kafka sink with two-phase commit via Flink checkpoints. On checkpoint, Flink commits pending Kafka offsets and sink transactions atomically. If a checkpoint fails, the source rewinds and the sink doesn't commit — no duplicates, no loss.

Cost: checkpoint interval trades latency for overhead. 30s is a good default for 100ms SLA.
