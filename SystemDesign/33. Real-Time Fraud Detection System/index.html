SYSTEM DESIGN · Capital One GPN · Senior Round

Real-Time Fraud Detection

Design a real-time fraud detection system that scores 12K transactions per second with <50ms latency, using rules + ML models, and adapts to new fraud patterns.

Scale: 12K tx/sec Latency: p99 < 50ms Accuracy: 95%+ recall, <1% false positive ML + Rules hybrid

1. Problem Statement

Design a fraud detection system for Capital One that evaluates every card transaction in real time. The system must score transactions in under 50ms, catch known fraud patterns (velocity, location, amount), adapt to new patterns using ML, and minimize false positives (declining a legitimate transaction loses customer trust).

Functional Requirements:

  • • Real-time scoring: Score every transaction in <50ms. Return approve/decline/review.
  • • Rules engine: Velocity checks, geo-velocity, blocklists, amount thresholds.
  • • ML scoring: Gradient boosted model on transaction features. Score 0-100.
  • • Case management: Review queue for borderline transactions. Analyst workflow.
  • • Feedback loop: Confirmed fraud feeds back into model retraining.
  • • Alerting: Notify customer of suspicious transaction via SMS/app.

Non-Functional Requirements:

  • • Latency: p99 < 50ms (customer waiting at POS)
  • • Throughput: 12K tx/sec peak
  • • Accuracy: 95%+ recall (catch 95% of fraud), <1% false positive rate
  • • Adaptability: Model retrains daily on new fraud patterns
  • • Explainability: Analysts must understand why a transaction was declined

2. Pattern Recognition

▶

Why signals:

  • • Real-time scoring with tight latency → pre-compute features, cache hot data
  • • Rules + ML hybrid → rules first (fast), ML for borderline
  • • Velocity checks (transactions per hour) → sliding window counters in Redis
  • • Model retraining → offline training, online serving with model versioning
  • • Feedback loop → event sourcing, confirmed fraud labeled and fed to training
  • • Explainability → SHAP values or feature importance for each decision

Core pattern: Two-tier scoring: fast rules engine (10ms) + ML model (30ms) for borderline. Redis for velocity features (sliding windows). Feature store for pre-computed aggregates. Model serving with versioning and A/B testing. Kafka for the feedback loop.

4. How to Think About It

▶

1 Why two-tier (rules + ML)?

Rules are fast (10ms) and explainable. They catch known patterns: "card used in 2 countries in 1 hour" or "merchant on blocklist." ML catches subtle patterns rules miss: "this transaction is 87% similar to a known fraud cluster." Rules handle 90% of decisions instantly. ML handles the 10% that rules flag as REVIEW. This keeps latency low and explainability high.

2 How do you compute velocity in real time?

Redis sliding window counters. For "transactions in last hour": a sorted set per card, keyed by timestamp. Count entries in the last 3600 seconds. O(log n) per update. For "amount spent in last 24h": a counter per card, incremented on each tx, decremented when entries expire. Pre-aggregated in Redis, not computed from raw events.

3 How do you handle model updates without downtime?

Model registry (MLflow) with versioned models. The scoring service loads models at startup and hot-swaps on signal. A/B testing: route 5% of traffic to the new model, compare metrics. If better, promote to 100%. If worse, roll back. No downtime, data-driven decisions.

4 → What about false positives?

False positives (declining a legitimate transaction) are worse than false negatives (missing fraud). A declined transaction loses customer trust and may cause them to switch cards. Tune the model to prioritize precision. For borderline cases, send to review queue instead of declining. Analyst feedback retrains the model.

5. Real-World Analogy

▶

Think of a nightclub bouncer with a metal detector and a behavioral analyst. The metal detector (rules engine) is fast: everyone passes through, it beeps if you have metal. 90% of people pass in 2 seconds. The 10% who beep go to the analyst (ML model) who looks at behavior, past history, and makes a judgment in 5 seconds.

The bouncer keeps a count of how many people entered in the last hour (velocity counter in Redis). If someone tries to enter 5 times in 10 minutes, that is suspicious. The blocklist is a photo book of known troublemakers (Redis set).

The feedback loop: if a fight breaks out inside, the bouncer notes the person's characteristics and adds them to the training data for the analyst (model retraining). Tomorrow, the analyst is better at spotting similar people.

6. Build Your Intuition

▶

Q: Why not just use ML for everything?

ML models are slower (30ms vs 10ms for rules), harder to explain ("the model said decline" is not actionable for an analyst), and harder to update (retrain vs update a rule). Rules catch the obvious cases fast. ML catches the subtle ones. Hybrid is the best of both.

Q: How do you handle the 50ms budget?

Rules: 10ms (Redis lookups). ML: 30ms (feature fetch + model inference). Decision combiner: 5ms. Kafka publish: 5ms. Total: 50ms. Pre-compute features in the feature store. Cache model in memory. Use gRPC for internal calls. No disk I/O on the hot path.

Q: What features does the ML model use?

Transaction features: amount, currency, merchant category, time of day. User features: historical spend pattern, average transaction amount, preferred merchants. Velocity features: transactions in last 1h/24h/7d, amount in last 24h. Context features: device, IP, geo distance from last transaction. ~50-100 features total.

Q: How do you deal with concept drift (fraud patterns change)?

Daily model retraining on the latest labeled data. Monitor model performance metrics (precision, recall) in production. If recall drops below threshold, trigger an alert. A/B test new models against the champion. The feedback loop from analysts and confirmed fraud cases is the key to adaptation.

7. How It Works (Step by Step)

▶
Step 1: Payment Service calls Fraud Gateway with transaction data (card, amount, merchant, location, timestamp).
Step 2: Fraud Gateway calls Rules Engine. Rules Engine checks Redis: velocity (tx count last 1h), blocklist (card, merchant, IP), geo (distance from last tx), amount threshold.
Step 3: Rules Engine returns: APPROVE (low risk), DECLINE (known fraud pattern), or REVIEW (borderline).
Step 4: If APPROVE or DECLINE, skip ML. Return decision. 90% of transactions stop here (10ms total).
Step 5: If REVIEW, call ML Scoring Service. Fetch pre-computed features from Feature Store. Run XGBoost model. Returns score 0-100 and top SHAP features.
Step 6: Decision Combiner: if ML score > 80, DECLINE. If 50-80, REVIEW (send to case queue). If < 50, APPROVE.
Step 7: Publish fraud.decision event to Kafka. Return decision to Payment Service. Total: 40-50ms.
Step 8: Async: Case Management creates a review case for REVIEW decisions. Analyst reviews, marks as fraud or legitimate. Feedback Service records the label.
Step 9: Daily: Model Training job pulls new labels from Feedback Service, retrains XGBoost, validates against holdout, registers new model in MLflow. A/B test against champion.

10. Scalability Deep Dive

▶

Throughput

12K tx/sec. Fraud Gateway: stateless, 50 pods. Rules Engine: stateless, 30 pods. Redis: 10-node cluster for velocity and blocklists. ML Scoring: 20 pods with model in memory. Feature Store: 5 replicas.

Latency

p99 < 50ms. Rules: 10ms (Redis pipeline). ML: 30ms (feature fetch 10ms + model inference 20ms). Decision: 5ms. Kafka publish: 5ms. 90% of tx skip ML, so p99 for those is 20ms.

Feature Store

Pre-computed user aggregates (30-day spend, merchant preferences) updated nightly. Real-time features (velocity) in Redis. Online feature fetch: 10ms from Redis + feature store. Offline training features from data lake.

Model Serving

XGBoost model loaded in memory (JVM/Python). 20ms inference for 100 features. Model versioned in MLflow. Hot-swap on signal. A/B test routing in Fraud Gateway. Champion vs challenger pattern.

Back-of-the-Envelope Estimation

12K tx/sec peak, 1B tx/day.

$$\text{Daily volume} = 10^9 \text{ tx} \quad \text{Fraud rate} \approx 0.1\% \Rightarrow 10^6 \text{ fraud cases/day}$$

Rules Engine: 90% of tx handled by rules. $$\text{Rules throughput} = 12{,}000 \times 0.9 = 10{,}800 \text{ tx/sec} \quad \text{ML throughput} = 1{,}200 \text{ tx/sec}$$

Redis velocity: sliding window 1h per card. $$\text{Keys} = 10^8 \text{ cards} \times 1 \text{ key} = 10^8 \text{ keys} \times 100 \text{ bytes} \approx 10 \text{ GB}$$

Feature Store: 100 features $\times$ $10^8$ users $\times$ 4 bytes $\approx 40$ GB. Model training: $10^9$ tx/day $\times$ 100 features, XGBoost retrain $\approx 30$ min on 100-core cluster.

11. Failure Modes & Resilience

▶

Rules Engine Timeout

Fail open (APPROVE) for low-risk transactions. Fail closed (DECLINE) for high-risk (e.g., amount > $5000). Circuit breaker: after 5 timeouts, stop calling rules, use ML only with a conservative threshold.

ML Scoring Service Down

Rules engine still works. For REVIEW decisions, fail open (APPROVE with post-transaction review) or fail closed (DECLINE). Business decision. Circuit breaker on ML service. Post-transaction review queue for fail-open cases.

Redis (Velocity) Down

Velocity checks fail. Fall back to ML-only scoring with a conservative threshold. Or fail open with post-transaction review. When Redis recovers, rebuild velocity from Kafka event replay.

Feature Store Down

ML scoring cannot fetch user features. Fall back to rules-only. Circuit breaker. When feature store recovers, ML resumes. Cache features locally for 5 min as a buffer.

Model Performance Degradation

Monitor precision/recall in real time. If recall drops below 90%, alert. If precision drops (too many false positives), alert. Roll back to previous model version. Investigate concept drift.

12. Edge Cases & Gotchas

▶

New card with no history

No velocity, no historical features. ML model has little to work with. Use a higher base risk score for new cards. Rules: lower velocity threshold. After 30 days of history, normal scoring applies.

Legitimate high-amount transaction

Customer buys a $5000 TV. Rules flag as REVIEW (high amount). ML sees: normal merchant, customer has history of large purchases, location matches. ML score low. APPROVE. The model must learn from the user's pattern, not just the amount.

Traveling abroad

Customer travels to Europe. Distance from last tx is 5000km. Rules flag as REVIEW. ML sees: customer has traveled before, ticket purchase pattern, hotel category. ML score low. APPROVE. Travel notification feature lets customers pre-notify.

Coordinated fraud attack

Fraudster tests 100 cards with $1 transactions. Each card looks normal individually. But the merchant or IP is shared. Aggregate-level rules: "same IP, 100 cards, 1 hour" triggers an alert. Graph-based ML can detect fraud rings.

Model bias and fairness

The model might disproportionately decline transactions from certain demographics. Monitor fairness metrics. Ensure features do not proxy for protected classes. Regular bias audits. Regulatory requirement.

13. Flashcards

▶
Q1: Why rules + ML hybrid?

Rules are fast (10ms), explainable, and catch known patterns. ML is slower (30ms), catches subtle patterns, but is harder to explain. Hybrid: rules handle 90% instantly, ML handles the 10% that rules flag as borderline.

Q2: How do you compute velocity in real time?

Redis Sorted Sets keyed by card_id, scored by timestamp. Count entries with score > (now - window). O(log n) per update. For amount velocity, store (timestamp, amount) and sum amounts in the window.

Q3: How do you handle model updates?

MLflow model registry. Champion vs challenger A/B testing. Hot-swap models in the scoring service. Monitor precision/recall. Roll back if performance degrades. Daily retraining on new labeled data.

Q4: What is the feedback loop?

Analyst reviews borderline transactions. Confirmed fraud and legitimate cases are labeled. Labels feed into daily model retraining. The model learns from its mistakes. This is how the system adapts to new fraud patterns.

Q5: How do you ensure explainability?

SHAP values for every ML decision: top 5 features that contributed to the score. Analysts see "declined because: high amount, unusual merchant, high velocity." This is actionable and builds trust. Regulatory requirement for credit decisions.

15. Common Mistakes

▶
  • • ML only, no rules. Slower, harder to explain, harder to update. Rules handle the obvious cases fast.
  • • Computing velocity from raw events. Too slow. Pre-aggregate in Redis sliding windows.
  • • No feedback loop. Model never improves. Analyst decisions must feed back into training.
  • • No explainability. "The model said decline" is not actionable. Use SHAP values. Analysts need to understand decisions.
  • • Ignoring false positives. Declining a legitimate transaction loses customers. Tune for precision. Review queue for borderline.
  • • No model monitoring. Concept drift degrades the model silently. Monitor precision/recall. Alert on degradation.
  • • No A/B testing for model updates. Blindly deploying a new model is risky. A/B test against the champion. Data-driven promotion.
  • • Ignoring aggregate-level fraud. Individual transactions look normal, but the pattern across cards is fraud. Graph-based detection catches fraud rings.

19. Trade-Offs

▶

Rules vs ML

Rules: fast, explainable, easy to update, but miss subtle patterns. ML: catches subtle patterns, but slower, harder to explain, harder to update. Hybrid gets the best of both at the cost of complexity.

False Positives vs False Negatives

False positive (declining legitimate tx) loses customer trust. False negative (missing fraud) loses money. For Capital One, customer trust is paramount. Tune for low false positives. Review queue for borderline.

Latency vs Model Complexity

A deep neural network might be more accurate but takes 100ms. XGBoost takes 20ms and is nearly as accurate. For the 50ms budget, XGBoost is the right choice. Deep learning for offline analysis.

Real-time vs Batch Features

Real-time features (velocity) are fresh but expensive to compute. Batch features (30-day aggregates) are cheap but stale. Use both: real-time for short windows, batch for long windows. Feature store bridges them.

Fail Open vs Fail Closed

Fail open: approve on service failure (customer experience). Fail closed: decline on failure (security). Business decision. Capital One: fail open for low-risk, fail closed for high-risk. Post-transaction review for fail-open.

20. Monitoring & Observability

▶

Model Performance Metrics

Precision, recall, F1, false positive rate, false negative rate. Tracked in real time. Alert if recall < 90% or false positive rate > 1%. Dashboard for model health.

System Metrics

Scoring latency p99, throughput, error rate, Redis hit rate, feature store latency, model inference time. Alert on SLO breaches.

Business Metrics

Fraud loss rate ($ fraud / $ total), decline rate, customer complaints, chargeback rate. These are the ultimate KPIs. Tracked daily. Reported to executives.

Fairness Monitoring

Decline rate by demographic group. If one group has a significantly higher decline rate, investigate bias. Regulatory requirement. Regular fairness audits.

A/B Test Monitoring

Champion vs challenger: precision, recall, latency. Statistical significance. Auto-promote if challenger is better. Auto-roll back if worse. No manual intervention.

21. Follow-Up Questions

▶
Q: How would you detect fraud rings (coordinated fraud)?

Graph-based detection. Build a graph: cards, merchants, IPs, devices as nodes. Edges: "card used at merchant," "card from IP." Fraud rings form dense subgraphs. Use community detection (Louvain) or graph neural networks. Neo4j or GraphX for processing.

Q: How would you handle real-time model updates (online learning)?

Online learning: update the model incrementally on each new label. XGBoost supports incremental training. Risk: model instability, no validation. Safer: micro-batch retraining every hour. Validate before promoting. Online learning is advanced and risky for production.

Q: How would you handle cross-channel fraud (card + ACH + wire)?

Unified customer view across channels. Velocity features span all channels. A customer with 10 card transactions and 5 ACH transfers in 1 hour is more suspicious than either alone. Feature store aggregates across channels.

Q: How would you handle model fairness and regulatory compliance?

Monitor decline rates by demographic. Ensure features do not proxy for protected classes (zip code can proxy for race). Regular fairness audits. Explainability for regulatory reviews. Model documentation for SR 11-7 (Federal Reserve model risk management).

Q: How would you reduce false positives without increasing false negatives?

Better features: add user behavior features (spending patterns, preferred merchants). Better model: ensemble XGBoost with a neural network. Review queue: send borderline to analysts instead of declining. Customer notification: push notification "did you make this transaction?" instead of declining.

23. Reference Implementation (Java)

▶

Rules Engine — Redis Sliding Window Velocity

import redis.clients.jedis.*;
import java.util.*;

public class RulesEngine {
    private final JedisCluster redis;

    public Verdict evaluate(Transaction tx) {
        // Velocity: count tx for this card in last 1 hour
        String key = "vel:" + tx.getCardId() + ":" + (System.currentTimeMillis() / 3600000);
        long count = redis.incr(key);
        redis.expire(key, 3600);

        if (count > 10) return Verdict.DECLINE;  // >10 tx/hr

        // Geo: check last known location
        String lastGeo = redis.get("geo:" + tx.getCardId());
        if (lastGeo != null && !lastGeo.equals(tx.getGeo())) {
            double dist = GeoUtils.distance(lastGeo, tx.getGeo());
            if (dist > 1000) return Verdict.REVIEW;  // impossible travel
        }

        // Blocklist check
        if (redis.sismember("blocklist:merchant", tx.getMerchantId()))
            return Verdict.DECLINE;

        return Verdict.APPROVE;
    }
}

ML Scoring — Feature Fetch + XGBoost Inference

import ml.dmlc.xgboost4j.java.*;
import java.util.*;

public class MLScoringService {
    private final Booster model;
    private final FeatureStore featureStore;

    public Score score(Transaction tx) throws Exception {
        // Fetch 100 features (10ms)
        float[] features = featureStore.getOnlineFeatures(tx.getUserId(), tx.getCardId());

        // XGBoost inference (20ms)
        float[][] input = {features};
        float[][] predictions = model.predict(input);
        float fraudProbability = predictions[0][0];

        // SHAP explainability (top 5 factors)
        List<String> topFactors = ShapExplainer.explain(model, features, 5);

        return new Score(fraudProbability, topFactors);
    }
}
