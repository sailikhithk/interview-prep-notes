Senior / Staff Defense Drills

Test your ability to spot architectural flaws and defend trade-offs out loud.

Q1: If DB write succeeds but cache eviction fails, how do you prevent stale reads without a TTL timeout? ↓

The Trap: Relying on in-memory application try-catch blocks to evict cache after DB transaction commits. If the server dies between the DB commit and Redis delete, cache stays stale indefinitely.

Senior/Staff Solution: Use Change Data Capture (CDC via Debezium/Canal) attached to the PostgreSQL WAL / MySQL Binlog. The CDC worker reads committed DB changes and asynchronously publishes cache invalidation events to Redis. This decouples cache invalidation from web request lifecycles.

Q2: Why is offset-based pagination (`OFFSET 10000 LIMIT 20`) banned at high scale? ↓

The Trap: The database must still read 10,020 rows from disk, sort them, and discard the first 10,000, causing massive I/O and query latency spikes ($O(N)$ scanning). Furthermore, concurrent row insertions cause duplicate or skipped records between page turns.

Senior/Staff Solution: Keyset / Cursor Pagination: `WHERE id > last_seen_id ORDER BY id ASC LIMIT 20`. This uses B-Tree index seeks directly ($O(\log N)$) without scanning preceding pages.

Q3: How do you invalidate stateless JWT tokens across 100 microservices immediately upon password reset? ↓

The Trap: Storing all tokens in a central database on every API call defeats the purpose of stateless JWT verification.

Senior/Staff Solution: Keep JWT verification local and cryptographic, but maintain a lightweight Revocation Bloom Filter / Redis Denylist at the API Gateway containing `(user_id, token_issued_before_timestamp)`. Set short JWT lifetimes (5-15 mins) paired with rotating refresh tokens.

Q4: In financial ledger systems, why is eventual consistency strictly forbidden? ↓

The Trap: Attempting to scale money transfers using asynchronous eventual consistency causes double-spend race conditions when a user transfers funds simultaneously on two devices.

Senior/Staff Solution: Strict serializable transactions or deterministic state machine replication. Double-entry bookkeeping where every debit has an equal and opposite credit ($ \sum \text{debits} = \sum \text{credits} $), with balance verification constrained in the DB.
