4. High-Level Design (HLD)

Two-tier: local token bucket per gateway node (in-process, sub-ms, absorbs bursts) + global Redis sorted set (source of truth, per-client fairness). Local bucket refills from Redis every 100ms; if Redis is down, fail open using local bucket alone.

5. Read & Write Data Flow Traces

Allow Flow (fast path)

  1. Request hits gateway node
  2. Local token bucket: check if token available
  3. If yes → decrement local bucket, forward request (0.1ms)
  4. Background: local bucket refills from Redis every 100ms
  5. Redis ZADD: add timestamp to client's sorted set
  6. ZREMRANGEBYSCORE: remove entries older than 60s
  7. ZCARD: count entries → if < limit, allow

Deny Flow (slow path)

  1. Local token bucket empty
  2. Gateway queries Redis sorted set
  3. ZCARD returns count > limit
  4. Return 429 with headers:
  5. X-RateLimit-Limit: 1000
  6. X-RateLimit-Remaining: 0
  7. Retry-After: 30 (seconds until oldest entry expires)

8. Distributed Coordination & State Management

No Raft needed. Redis cluster (10 shards, hash by api_key) is the coordination primitive. Local token buckets are eventually consistent with Redis — 100ms sync interval.

Local Bucket Sync

  • Refill interval — 100ms background task
  • Refill amount — (limit / 600) tokens per 100ms
  • Cap — never exceed burst size
  • Fail open — if Redis down, use local only

Config Broadcast

  • Store — DynamoDB config table
  • Broadcast — Redis Pub/Sub to all nodes
  • Cache — in-process, 5s TTL
  • Rollback — instant via new config publish

9. Partitioning & Database Scaling

Redis: Shard by api_key

  • 10 shards — 100K RPS / 10 = 10K ops/shard
  • Hash slot — CRC16(api_key) mod 16384
  • Hot client — split by api_key + endpoint

  • In-process — Caffeine cache, no network
  • Key — {node_id, api_key}
  • Eviction — LRU, 10K entries per node
  • Size — ~50 bytes per entry → 500KB/node

Java — Token Bucket + Redis Sorted Set

public class DistributedRateLimiter {
    private final RedisClient redis;
    private final Cache<String, TokenBucket> localBuckets;
    private final RateLimitConfig config;

    public RateLimitResult check(String apiKey) {
        // 1. Try local bucket first (fast path)
        TokenBucket bucket = localBuckets.get(apiKey, k -> new TokenBucket(config));
        if (bucket.tryConsume()) {
            return RateLimitResult.allow(bucket.remaining());
        }
        // 2. Fall back to Redis sorted set (slow path)
        String key = "rate_limit:" + apiKey;
        long now = System.currentTimeMillis();
        long windowStart = now - (config.getWindowSec() * 1000L);

        // Lua script for atomicity
        String lua = """
            redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1])
            local count = redis.call('ZCARD', KEYS[1])
            if count < tonumber(ARGV[2]) then
                redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])
                redis.call('EXPIRE', KEYS[1], ARGV[5])
                return {1, tonumber(ARGV[2]) - count - 1}
            else
                return {0, 0}
            end
            """;

        Object[] result = redis.eval(lua, List.of(key),
            List.of(String.valueOf(windowStart),
                    String.valueOf(config.getLimitRpm()),
                    String.valueOf(now),
                    UUID.randomUUID().toString(),
                    String.valueOf(config.getWindowSec() * 2)));

        boolean allowed = ((Long) result[0]) == 1;
        long remaining = ((Long) result[1]);

        if (allowed) {
            bucket.refill(config.getRefillAmount());
            return RateLimitResult.allow(remaining);
        } else {
            long retryAfter = config.getWindowSec() - (now % (config.getWindowSec() * 1000L)) / 1000;
            return RateLimitResult.deny(retryAfter);
        }
    }
}

Python — Sliding Window Log

import time, uuid, redis
from dataclasses import dataclass

@dataclass
class RateLimitConfig:
    limit_rpm: int = 1000
    window_sec: int = 60

class SlidingWindowLimiter:
    def __init__(self, redis_client: redis.Redis, config: RateLimitConfig):
        self.r = redis_client
        self.config = config

    def check(self, api_key: str) -> dict:
        key = f"rate_limit:{api_key}"
        now_ms = int(time.time() * 1000)
        window_start = now_ms - (self.config.window_sec * 1000)

        # Atomic Lua script
        lua = """
        redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1])
        local count = redis.call('ZCARD', KEYS[1])
        if count < tonumber(ARGV[2]) then
            redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])
            redis.call('EXPIRE', KEYS[1], ARGV[5])
            return {1, tonumber(ARGV[2]) - count - 1}
        else
            return {0, 0}
        end
        """

        allowed, remaining = self.r.eval(
            lua, 1, key,
            window_start, self.config.limit_rpm,
            now_ms, str(uuid.uuid4()),
            self.config.window_sec * 2
        )

        if allowed == 1:
            return {"allowed": True, "remaining": remaining}
        else:
            retry_after = self.config.window_sec
            return {"allowed": False, "remaining": 0, "retry_after": retry_after}

14. Resiliency & Failure Mitigations

⚡ Redis Down

Redis cluster unavailable. Mitigation: fail open using local token bucket only. Each node allows up to (limit / num_nodes) per second. Slight over-allowing but no outage. Alert P1.

⚡ Hot Client

One client dominates traffic, causes Redis hotspot. Mitigation: split key by api_key + endpoint. Or use local-only limiting for that client (less accurate but no hotspot).

⚡ Clock Skew

Gateway nodes have different clocks. Mitigation: use Redis TIME for timestamp in Lua script (server-side). Local buckets use NTP-synced clocks, 50ms skew tolerance.

⚡ Config Propagation Delay

New limit takes time to reach all nodes. Mitigation: Pub/Sub broadcast (1s), 5s TTL poll fallback. Worst case 6s skew — acceptable for rate limits.

⚡ Gateway Node Down

A gateway pod crashes. Mitigation: local bucket state lost, but Redis has the truth. New pod starts with empty local bucket, refills from Redis. No over-allowing.

⚡ Redis Memory Full

Sorted sets grow too large. Mitigation: TTL on every key (2x window). Eviction policy: allkeys-lru. Monitor memory, alert at 80%.

19. Handling Interviewer Pushbacks

Q: "What if Redis goes down — do you fail open or closed?"

"Fail open. Rate limiting is a secondary concern — we'd rather over-allow than block legitimate traffic. Each node continues with its local token bucket, allowing limit/N per second. We alert P1 on Redis down and page the on-call. If we fail closed, a Redis outage becomes a full API outage, which is worse."

Q: "How do you handle a hot client that overwhelms one Redis shard?"

"Three options: (1) split the key by api_key + endpoint, distributing across shards. (2) Use local-only limiting for that client — less accurate but no hotspot. (3) Promote the client to a dedicated Redis shard. I'd start with option 1, then option 3 if the client is consistently hot."

Q: "Why token bucket instead of sliding window?"

"Token bucket allows bursts — a client can save up tokens and make a quick burst of requests. Sliding window is stricter but less flexible. For APIs, token bucket is the standard — it handles legitimate bursts (a client loading a dashboard) while enforcing an average rate. I use sliding window log in Redis as the source of truth because it's exact, and token bucket locally for speed."

Q: "How accurate is this? Can a client exceed the limit?"

"Yes, slightly. The local bucket can over-allow by up to (limit/N) per node during the 100ms sync window. Worst case: a client gets limit + (N-1) * (limit/N) * 0.1s skew ≈ limit * 1.1. That's 10% over, within our 1% error budget if we tune the local bucket to 90% of per-node share. The Redis path is exact — the over-allowing is only during local bucket depletion."

Q: "How do you test this at scale?"

"Three levels: (1) unit tests for the algorithm — token bucket, sliding window. (2) integration tests with a real Redis — verify atomicity, TTL, eviction. (3) load tests with 100K RPS against a staging cluster — measure p99 latency, Redis QPS, failover behavior. We also run chaos tests — kill Redis shards, gateway nodes, network partitions — and verify fail-open works."

20. Advanced Concept Deep Dives

▶ Token Bucket vs Sliding Window vs Leaky Bucket

Token bucket: tokens added at fixed rate, consumed per request. Allows bursts up to bucket size. Best for APIs.

Sliding window log: stores timestamps of all requests in window. Exact but memory-heavy. Best for source of truth.

Sliding window counter: divides window into sub-windows, counts per sub-window, extrapolates. Approximate but memory-light.

Leaky bucket: requests enter queue, processed at fixed rate. Smooths bursts but adds latency. Best for message queues.

▶ Lua Script Atomicity in Redis

Redis executes Lua scripts atomically — no other command runs during the script. This is critical for rate limiting: ZADD + ZREMRANGEBYSCORE + ZCARD must be atomic, or two concurrent requests could both see count < limit and both be allowed.

Optimization: Redis caches compiled Lua scripts by SHA. Use EVALSHA instead of EVAL to avoid re-sending the script. Saves bandwidth at 100K RPS.

▶ Fairness and Noisy Neighbor Problem

Without per-client limits, one noisy client can degrade service for all. The distributed limiter enforces per-client fairness: each client gets their configured rate, regardless of others. For shared resources (a single backend), add a global limit on top — but that's a circuit breaker, not a rate limiter.

Edge case: a client with 1000 req/min limit can still cause issues if they burst all 1000 in 1 second. Token bucket with burst=100 prevents this.

▶ Anycast and Geo-Distributed Limiting

For global APIs, clients hit the nearest gateway (anycast). Each region has its own Redis cluster. Global limits require aggregation: each region gets limit/N, and a periodic sync reconciles. This is eventually consistent — a client could exceed the global limit by up to (N-1) * region_limit during sync. For exact global limits, use a single Redis region (adds latency).

▶ Adaptive Rate Limiting

Static limits don't account for backend health. Adaptive limiting adjusts based on response times, error rates, or queue depth. If p99 > 500ms, reduce limit by 20%. If healthy, increase by 5%. This is a feedback loop — the limiter monitors the backend and adjusts. Used by Stripe, GitHub. More complex but more resilient.

▶ Client-Side Rate Limiting

The server returns X-RateLimit-Remaining and Retry-After headers. Well-behaved clients use these to throttle themselves — avoiding 429s. This reduces server load but can't be trusted (malicious clients ignore headers). Server-side limiting is the source of truth; client-side is a courtesy.
